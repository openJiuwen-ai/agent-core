# 收敛通知关闭与审批恢复接管边界

## 1. 定位、目标与范围

只修复现有通知清理和停止成员审批恢复中的两个局部边界。原审批卡绑定、消费证据、
checkpoint 身份、成员启动确认、关流前审批复查和 memory SQLite 读写互斥继续有效。
原停止成员恢复设计仅补充接管资格的事务边界，不整体替代。

- 通知回调直接调用并等待自身团队停止时，关闭路径应完成，而不能等待这个调用者退出。
- 审批预检与真正接管之间新增的普通未读消息，应使本次审批恢复资格失效；不得因此启动停止成员。
- 不增加公共 API、schema、重试队列或通用任务管理器；不重构全局广播、所有 DAO 或全部生命周期入口。

## 2. 已核实机制与约束

通知任务先读取已持久化消息，再直接等待宿主回调。当前关闭入口同时取消和等待通知任务，
因此回调内的停止调用可能等待自己的任务。数据库读取需要完整结束，宿主回调不需要由框架等待。

审批恢复先检查邮件，再调度独立恢复任务；后者只按 STOPPED 状态抢占。新增普通邮件可以在
两阶段之间落库。当前 S_03 要求目标停止成员仅持有合法审批未读。

TeamDatabase 已负责跨 DAO 事务，DbSessions.write 已拥有写事务和进程内写锁。
MessageDao 已有接收人、广播水位和群通知的会话内查询；不得在持有 write 锁时再开启 read/write。
恢复仅适用已证明身份的同进程原生成员；未知 checkpoint、第三方 provider 和跨会话恢复仍保留邮件。

## 3. 通知清理方案

### 3.1 区分框架读取与宿主回调

在 GroupMessageHandler 内保留现有通知任务集合，增加一个私有的在途消息读取 task 集合。
读取 task 必须在首次 await 前登记，在真正完成时移除；沿用现有反复 shield、延迟传播取消的 helper，
保护完整 get_message 及 DAO session 清理。回调仍在读取结束后运行，仍受现有通知超时约束。

### 3.2 关闭顺序

kernel 继续先停事件分发，再调用同一取消入口：

1. 对通知任务取快照；若当前任务本身就是通知任务，跳过它的主动取消。
2. 取消其余通知任务，保持正在取消的任务不重复主动 cancel。
3. 只等待已登记的框架数据库读取，不等待宿主回调及其返回。
4. 在途读取清理完成后才允许 kernel 释放会话；等待自身的取消仍在读取清理后传播。

上述步骤在取得通知和读取快照之间不挂起。未开始的通知被取消后不会再启动查询；
已经开始的查询必已登记；停止分发后没有新的生产调度入口。
当前回调在停止返回后自行结束，通知集合由原 done callback 移除，不能在关闭入口伪造“所有回调已退出”。

只保护框架拥有的消息读取；宿主回调自行创建的资源仍归宿主。保留外部取消语义，
不承诺不可取消的整个 stop，也不把通知的 10 秒超时解释为全局关闭上限。

### 3.3 取舍

仅从 gather 排除当前 task 不足以防止多个回调互相等待。等待所有回调也没有数据库安全上的必要。
不新增回调调度器或改成 fire-and-forget；只修改本地资源等待范围。

## 4. 审批恢复方案

### 4.1 原子资格与抢占

保留原预检及 checkpoint 校验，用合法审批邮件 ID 集合作为本次候选。
新增 TeamDatabase 的私有跨表接管操作，由 RecoveryManager 调用：

1. 只打开一次 DbSessions.write，复用同一个 session。
2. 在事务中先按团队、成员、角色及 STOPPED 条件占用成员行，写入尚未提交的 RESTARTING。
   复用 MemberDao 的会话内 CAS 逻辑，不在辅助方法中提交。
3. 在同一事务 session 中核对：未读直达邮件仍恰好是已验证的 leader 审批集合，
   且成员没有普通广播、被提及群消息或群通知形成的未读输入。
   复用 MessageDao 现有接收人、水位与群通知规则，不复制一套消息资格解释。
4. 不符合则 rollback 并返回未接管；符合才 commit 并返回已接管。
5. commit 完成后才创建恢复 handle；之后沿用原订阅、READY 接管和开放邮箱流程。

先占用成员行的 DML 也使 SQLite 在读取资格前进入真实写事务，避免依赖旧驱动对 SELECT 的隐式事务行为。
事务内不创建模型、启动 runtime、发布事件或读取外部存储。预检已验证邮件内容，事务内只核对不可变邮件身份与未读状态。
现有普通 claim_member_restart 的公开内部调用方式和其他恢复路径不改变；只提取 session 级复用 helper。

取消时仍须等事务结果确定：未提交的操作 rollback；已提交的 RESTARTING 交还给原有条件回滚与清理。
不得因外部取消在未知提交结果时放弃状态归属。等待须覆盖重复取消；不能沿用首次 shield 后直接 await claim 的单次取消处理。

### 4.2 线性化和兼容边界

本次承诺：成员行被本次事务占用前已提交的普通未读，必参与资格判断并阻止接管。
与接管事务重叠的输入按接管先后归属；不承诺整套跨进程信箱的全局提交顺序。
接管成功的成员仍按现有恢复语义进入正常运行，后续消息沿用现有邮箱规则。

不新增常驻“只读审批”运行模式，不改变 READY 成员的正常收件能力。此处对评审建议的取舍是：
以原子资格判断消除“普通邮件已经存在但仍接管”的实证问题，而不是重新定义恢复实例的整个生命周期。

资格变化造成的未接管仅在当前预约仍属于本 task 时释放，允许下轮重新预检；
成功接管和启动失败的本轮尝试记录不能在 done callback 中统一删除。实际接管后的启动失败仍沿用
每成员每轮一次、精确状态回滚和停机取消。不得新增立即循环或无界重试。

### 4.3 取舍

只在恢复 task 开头再查一次邮件仍有检查与 CAS 的间隙。跨启动全过程持有数据库锁会把模型、
订阅和 runtime 启动放进写事务，不采用。移除审批恢复或引入常驻审批专用 runtime 都会改变已确认行为，
不作为本次两个局部回归的默认修法。

## 5. 修改范围与契约同步

目标代码范围：
- group_chat/message_handler.py；kernel 仅在调用契约需要时改动。
- agent/recovery_manager.py 与 spawn_manager.py 的本次接管预约。
- tools/database/__init__.py、member_dao.py、message_dao.py 的窄事务复用点。
- 两类问题的现有邻近测试。

实施时同步 S_28 的“排空框架读取而非宿主回调”，以及 S_03 的接管资格原子性与限次定义；
在现有缺陷记录追加实际验证。本文只记录方案，不冒充代码已修复。

## 6. 验证设计

1. 宿主回调直接等待 stop_team：应关流、释放会话、移除 pool，回调能够返回。
2. 两个回调同时请求停止：不能因互等通知任务形成新环；不据此承诺完整的生命周期串行化。
3. 其他通知的读取处于锁等待或 cursor 阶段：stop 必须等这些读取清理，成员与消息仍存在。
4. 慢回调、通知超时、反复取消和查询异常：保持既有可取消行为与读取保护；不得要求通知集合在返回时立即为空。
5. 预检后、事务占用成员前插入普通广播或普通直达邮件：事务不接管，无新 handle，消息和审批保持未读。
6. 已有非审批输入，以及群提及、群通知、水位边界：新事务与现有接收人资格一致。
7. 新合法审批改变候选集合：本次保留邮件且不创建 handle；后续预检可重新取得资格，无立即重试循环。
8. 正常过期审批可清理、匹配审批只执行一次；未知身份、装载失败、订阅失败、READY 提交与取消竞争仍保持原断言。
9. 在 memory/file SQLite 验证事务 rollback、CAS 持久性与事务重复取消后的状态归属；可用的其他数据库只做相应集成验证，不虚称已运行。
10. 接管成功后、READY 前到达的普通输入沿用正常收件语义；与接管前必须拒绝的场景形成明确对照。

实施后的验证先覆盖上述两个复现，再运行原审批、数据库、群聊和生命周期定向回归；遵守仓库不运行静态工具的要求。
