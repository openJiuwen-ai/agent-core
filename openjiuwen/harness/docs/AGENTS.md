# harness/docs

本目录维护 Harness 的公共设计规约、特性记录和文档模板。本文规定文档组织与维护方式，
也供模块文档目录显式引用；模块设计写入对应文档，代码行为以实现和测试为准。

## 适用范围与规则入口

- 本目录及明确引用本文的模块文档目录，采用下述公共文档规范；各模块在自己的
  `docs/AGENTS.md` 中保留职责边界、具体设计入口和专属流程。
- 本文集中维护文档组织、开发同步及提交约定；模块的运行架构、接口与行为约束在相应
  spec 和 feature 中说明。

## 文档分类与目录用途

| 目录 | 用途 | 创建或更新时机 |
| --- | --- | --- |
| `specs/` | 当前已确认的接口、状态、边界和不变量 | 新契约形成或已有契约变化时同步维护 |
| `features/` | 一项完整特性或重构的设计记录，解释背景、决策、取舍和验证 | 实现前建立方案，开发中补充决策与证据，落地后保留历史记录 |
| `templates/` | 公共文档模板及填写、维护规范 | 通用写作要求变化时更新，本目录统一维护 |
| `designs/`（模块按需设置） | 概览、架构方案、开发计划、备选设计及待验证问题 | 需要整体说明、方案讨论或交付计划时创建，并标明确认与实现状态 |

`specs/` 维护契约，`features/` 解释契约为何变化；概览和架构维护整体设计，开发计划维护
特性拆分与执行进展。它们通过引用关联，同一接口、验收要求或当前进度只维护一份。
按已有主题和实际设计需要创建文件，不预建空白 spec 或 feature，也不为套用模板新建目录。

## 命名与编号

```text
specs/S_NN_<slug>.md
features/F_NN_<slug>.md
designs/<slug>.md
```

- `NN` 使用两位递增序号；新增编号取本目录该类型已使用的最大编号加一。
  编号由各模块、各类型独立管理，不按当前文件数量计算；删除后的历史编号不复用，
  必要时核对 Git 历史，不回填空缺。
- `<slug>` 使用简短英文小写单词，以短横线连接；下划线只用于 `S_NN_` / `F_NN_` 前缀。
  文件名不带日期，`designs/` 使用描述性名称，不占用 spec 或 feature 编号。
- 日期写入元信息，使用 `YYYY-MM-DD`；spec 修订更新最近一次修订日期，feature 保留归档日期
  并记录后续修订日期。不在元信息中写 commit hash。
- 一项连贯的设计变更归档为一份 feature，不按提交次数拆分；后续修订保留原编号和历史决策。
  已有 feature 归档不删除，过时结论标明适用范围和当前替代关系。

## 模板与必要内容

新增或修改相关文档前，必须阅读并参考以下相应模板的填写与维护要求。模板章节可按实际
范围裁剪，但不能省略适用的契约、决策或验证要求，也不能直接保留占位内容作为设计结论。

| 文档类型 | 模板 |
| --- | --- |
| 设计概览（Overview） | [overview-template.md](templates/overview-template.md) |
| 架构详细设计 | [architecture-template.md](templates/architecture-template.md) |
| 模块规约（spec） | [spec-template.md](templates/spec-template.md) |
| 特性设计（feature） | [feature-design-template.md](templates/feature-design-template.md) |
| 特性开发计划与进度 | [feature-development-plan-template.md](templates/feature-development-plan-template.md) |

- spec 必须明确范围、接口与错误语义、状态及数据生命周期，并编号列出不变量。
  引用其他 spec 的契约，不复制其定义。
- feature 必须解释背景、采用方案的决策、被放弃的方案及原因、契约影响、验证和遗留；
  不能只复述提交记录。
- 目标方案、已确认待实现的契约、已实现行为及待验证前提分别标明状态。
  spec 可记录已确认待实现契约，但必须明确接入缺口；尚未确认的备选方案放入设计文档，
  不能作为已生效接口或能力保证。
- 关联现有实现的路径和符号必须能在代码中核对；拟议路径、接口及示意代码须明确标注。
  当前契约与历史结论分开表达，不将旧编号、旧门槛或历史验证结果当作当前状态。

## 开发与文档同步

1. 开发前先阅读相关 spec 和 feature，在 `features/` 新增或更新本次特性方案，说明范围、
   设计与验证方式，再按方案实现。
2. 接口、状态、不变量或职责变化时，及时同步其归属 spec，用 feature 记录设计原因；
   涉及整体方案时同步概览、架构及开发计划。架构调整的确认流程由模块补充规则规定。
3. 发现文档与代码或测试不一致时，先核对实现，修正过时事实；涉及改变已确认架构方案时，
   按适用确认流程处理，不能把过时描述当作新实现依据。
4. 验证记录写明实际范围、环境、入口、结果和剩余项。未执行不能写成通过，模拟组件验证
   不能扩大解释为真实宿主或完整业务闭环；部分验证和历史结果须标明边界。
5. 特性认领与进度按下节在所属模块的统一计划中维护；具体计划入口由模块规则指定。

跨模块契约在公共 spec 中维护，模块专属契约在所属模块的 spec 中维护，`AGENTS.md` 只放
适用规则与阅读入口。`CLAUDE.md` 是只读引用壳，文档规则的修订写入对应 `AGENTS.md`。

## 特性认领与进度维护

- **统一维护位置：** 模块指定一份开发计划或既有统一进度表，集中维护当前负责人、状态和
  证据；概览、架构和 feature 引用该位置，不另建重复的当前进度台账。
- **新增特性：** 补充目标与范围、独立验收标准、最小开工硬前置、工作线和交付节点；
  同步依赖关系、进度条目、特性总数与统计摘要。计划条目和 feature 文件编号分别管理，
  在方案与计划之间建立明确关联，不默认两者编号相同。
- **认领与开工：** 核对当前范围和必需前置，在统一进度表登记负责人及安排；建立或更新
  feature 方案，开始设计、实现或验证时更新状态。
- **进展变化：** 及时更新状态、已完成范围、验证环境和实际结果、证据链接、关联 PR 及
  最近更新，保留历史证据；阻塞时说明缺口、责任方、影响与解除条件。
- **联动更新：** 范围、契约或依赖变化时，同步特性定义、关系图、进度条目和受影响节点，
  记录变更原因；常规进展只更新进度与证据，不重复改写验收要求。
- **完成判断：** 使用所属计划已有状态和统计口径，按约定验收范围登记结论。
  部分组件或模拟验证通过不代表整项完成；真实联调须说明对端版本与环境，
  不以代码写完或 PR 合并代替特性验收。

## 引用与提交检查

### 提交约定

- Harness 模块的 commit message scope 固定为 `harness`，例如 `feat(harness): ...`、
  `test(harness): ...`、`docs(harness): ...`。
- footer 使用 `Refs: #<issue>` 关联 Issue；当前上下文不能明确编号时，提交前向开发者询问，
  不臆造编号或填写空引用。
- 涉及特性实现及相关 spec / feature 更新时，特性代码、测试代码与文档拆成三个连续提交，
  顺序为实现（`feat` 或适用的 `fix` / `refactor`）→ 测试（`test`）→ 文档（`docs`）。
  文档提交包含本次 feature 归档与关联 spec 修订，不把无关改动混入同一工作单元。
- 特性开发须形成设计归档；不能确定某项改动属于特性还是普通修复时，先向开发者确认，
  歧义情况下按需要归档处理。

### 引用与一致性检查

- 文档链接使用相对路径，并从引用所在文件的目录计算；跨仓引用注明仓库和路径。
  不直接复制模板的示例路径，引用文件移动或删除时同步检查关联文档。
- 本文中的模板链接相对于本文件；模块文档须重新计算。提交前核对链接目标存在且可打开，
  章节引用与当前结构对应，文件名、编号和元信息符合约定。
- 修改后核对文档、实现与验证证据的一致性，并运行 `git diff --check`。
