# persistent_agent/docs

`openjiuwen.harness.persistent_agent` 的设计文档目录。这里记录 Persistent Agent 的
通用执行契约、设计决策与特性变更；代码行为以实现和测试为准。本文规定文档的组织方式、
开发中的设计确认与同步，以及特性计划和进度维护。
具体设计写入对应文档，不写入本 `AGENTS.md`。

当前不预建空白的 spec 或 feature 文件；随着模块设计和实现逐步形成，再按主题创建。

## 目录用途

| 目录 | 用途 | 何时创建或更新 |
| --- | --- | --- |
| `designs/` | 方案草稿、备选设计和待验证问题；可以描述尚未实现的目标 | 需要讨论跨模块方案，但契约尚未确定时 |
| `specs/` | 长期有效的模块规约，描述当前已确认的接口、状态、边界和不变量 | 新增规约时创建；已有关联契约变化时同步修订 |
| `features/` | 一次完整特性或重构的设计记录，解释背景、决策、取舍与验证 | 开发前新增或修改设计，开发中补充决策与验证，落地后归档；保留历史决策 |

`specs/` 描述当前契约，`features/` 解释契约为何变化，`designs/` 保存尚待确认的方案。
目标设计与已实现行为必须标明状态，不能把设计设想写成已经生效的接口。

## 范围与边界

- 本目录只记录 `agent-core` 中 Persistent Agent 的通用能力，例如指定 Session 内的执行、
  调用状态隔离、上下文组装、活动窗口和归档、历史检索、资产访问及恢复现场重建。
- Agent 配置发布、渠道绑定、会话排队与执行权、结果提交和投递等 JiuwenMate 服务端职责，
  在 `jiuwenswarm` 仓维护。跨仓接口在本目录记录 Persistent Agent 一侧的输入、输出与约束，
  并标注对端文档或代码位置。
- PersonalContext 的采集与发布实现位于 `openjiuwen/harness/personal_context/`；
  本目录只记录 Persistent Agent 如何取得获授权的知识版本并在模型调用前使用它。
- 不复制 `openjiuwen/harness/docs/` 已有的 DeepAgent、Rail、工具和工作空间通用规约；
  涉及这些公共契约时引用原文档，并在公共契约变化时同步更新其归属文档。

## 命名规约

```text
specs/S_NN_<slug>.md
features/F_NN_<slug>.md
designs/<slug>.md
```

- `NN` 使用两位递增序号，从目录内现有最大编号加一开始；不复用已有编号。
- `<slug>` 使用简短的英文小写单词，以短横线连接；文件名不带日期。
- 日期写在文档元信息中。`designs/` 的草稿可使用描述性文件名，不占用 spec 或 feature 编号。
- 一项连贯的设计变更归档为一份 feature 文档，不按提交次数拆成多份。

## 内容约定

### `specs/` 建议结构

```markdown
# <规约名称>

## 元信息
| 项 | 值 |
| --- | --- |
| 类型 | spec |
| 关联模块 | openjiuwen/harness/persistent_agent/<path> |
| 最近一次修订日期 | YYYY-MM-DD |
| 关联 feature | F_NN_<slug>.md（如适用） |

## 范围与边界
## 不变量
## 接口契约与错误语义
## 状态及数据生命周期
## 与其他规约的关系
```

### `features/` 建议结构

```markdown
# <特性名称>

## 元信息
| 项 | 值 |
| --- | --- |
| 类型 | feature |
| 日期 | YYYY-MM-DD |
| 范围 | <修改路径> |
| 测试基线 | <实际验证结果> |
| Refs | <关联 issue，如适用> |

## 背景
## 决策
## 拒绝的方案及原因
## 对契约与状态的影响
## 验证
## 已知遗留
```

小节可按实际改动调整；`features/` 应解释为何采用当前方案，以及为何放弃其他方案，
不能只复述提交记录。没有运行过的测试不得写成已通过。

## 开发流程与同步

### 特性设计先于实现

- 开发特性前，先在 `features/` 新增或修改对应的特性设计文档，写清本次实现的范围和设计，
  再按该设计开展代码开发。
- 尚未实现的内容明确标为待实现；开发过程中补充实际决策和验证结果，不能把计划中的验证写成已通过。

### 架构设计变更与 spec 同步

- 代码实现过程中若需要调整[架构设计文档](designs/persistent-agent-architecture.md)，先向开发者说明
  拟修改的设计内容、原因和对当前特性的影响，取得确认后再修改架构设计文档，并按确认后的方案实现。
  未经确认，不擅自改写架构设计文档。
- 开发过程中若改变了 spec 所描述的接口、状态、不变量或其他契约，及时更新 `specs/` 中对应的
  spec 文档，使其与实现保持一致，并用 feature 记录设计原因；
  新主题按需创建文件，不为未来主题预留空文档。
- 阅读文档时若发现描述与代码或测试不一致，先核对实现；涉及架构设计调整时遵循上述确认流程，
  其他过时描述及时修正，不能作为新实现的依据。

### 特性认领与进度维护

- 新增特性时，及时更新[特性计划、开发顺序与进度跟踪](designs/persistent-agent-development-plan.md)：
  补充特性条目、开工硬前置、所属并行工作线与交付节点，并同步特性总数和进度信息。
- 认领特性时，及时在计划文档对应特性的“负责人”列登记；开始开发时更新“状态”。
- 开发、阻塞、验证和完成的进度变化，及时更新计划文档中的“状态”“证据”、相关交付节点及变更记录。

## 引用与提交

- 文档间优先使用相对路径链接，引用跨仓内容时写明仓库和路径，避免仅凭同名模块定位。
- 特性代码、测试和文档的提交规则遵循上级 `openjiuwen/harness/AGENTS.md`；
  本文件不重复定义提交顺序或 scope。
