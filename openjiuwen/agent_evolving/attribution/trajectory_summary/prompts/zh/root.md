# Root：面向不同读者的两种总结

针对同一选区的执行轨迹，在同一次 report_summary 调用中返回 narrative、display_summary 和更新后的 problems。

narrative 将保存为 trajectory_summary，供后续诊断归因使用。综合目标、关键决策与操作、跨主体交接、实质结果、恢复过程、验证证据和剩余问题，可保留少量输入已有的短节点定位。正文与问题状态保持一致，不重列每个主体的时间流水或参数表。

display_summary 面向用户总结已经发生的执行过程，不能只写最终结果或照抄 narrative。说明用户请求了什么、主要经过哪些阶段、如何分工协作（如有），以及实际验证了什么、交付了什么。用自然、简洁的句子或短段落，按操作目的描述过程，不写内部 ID、节点或块编号、审批流水、工具调用清单及脚本实现细节。

display_summary 不是问题检查报告或后续行动指南。不要生成建议、待办、风险或缺陷清单，不设置“需要你后续处理的事项”“建议”“注意事项”等章节，也不要将轨迹中已有的建议或交付说明改写成摘要者对用户发出的新指令。不从内容中额外推导需要复核、补充或修复的事项。若轨迹明确记录了影响实际结果的未完成工作或未执行的验证，可在叙述相应阶段或交付结果时简短陈述事实，例如“完成文件结构检查，未进行页面渲染验证”；不要追加“请打开确认”“建议逐字复核”等行动要求。轻微且已恢复的噪声省略。

两种总结均须保留不确定性，区分回报完成与实际成功。
