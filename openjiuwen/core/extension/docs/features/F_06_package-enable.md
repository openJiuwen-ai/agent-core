## 1. 背景、目标与范围

扩展包安装后，现有 Core 只能将它加载为生效状态，或者通过卸载删除安装副本。本特性增加保留安装副本的启用状态，供宿主按自身交互或恢复策略控制是否加载包代码。

| 场景 | 目标行为 |
| --- | --- |
| 安装的 manifest 未声明 `enable` | 解析时按 `true` 使用，写入受管安装副本时补写 `"enable": true` |
| 安装的 manifest 声明 `enable: false` | 校验并复制到安装目录，但不加载模块、不发布 Handler 或 MCP 声明 |
| 已安装包切换为禁用 | 注销该包的 Handler 和受管理资源，保留安装副本并将 `enable` 写为 `false` |
| 已安装包切换为启用 | 将 `enable` 写为 `true`，按正常安装路径校验、加载和发布 |
| 已禁用包执行重载 | 成功返回，不导入模块、不发布 Handler 或 MCP 声明，`enable` 保持 `false` |

本次不提供产品界面、持久化操作历史或跨进程协调策略；宿主负责这些能力及调用时机。启用/禁用不撤销已启动的业务调用，也不是不可信 Python 代码的隔离措施。

## 2. 方案与取舍

`enable` 保存为包根 `manifest.json` 的顶层字段，是安装副本的期望加载状态。Core 只提供与包、目录和 Runtime 有关的通用接口，不识别任何宿主、服务或产品概念。

禁用复用卸载的注销、资源清理和依赖保护流程，但不删除受管目录；启用复用安装的计划、依赖校验和发布流程。这样包代码只会在启用流程通过校验后导入，状态、文件和生效记录分别由 Package Manager、Runtime 与安装报告维持。

未采用由宿主自行编辑 manifest 的方案：该方案会绕过 Core 的目录校验、运行锁、资源清理和报告提交，无法保证活动 Handler 与文件状态一致。

## 3. 详细设计

### 3.1 数据与接口

`Manifest.enable: bool = True` 映射顶层 `enable`。缺失字段的语义固定为 `true`，非 bool 拒绝为 `EXTENSION_MANIFEST_INVALID`。

| 入口 | 责任 | 完成条件 |
| --- | --- | --- |
| `PackageManager.normalize_legacy_enable` | 为受管旧副本补写缺失字段 | 原子替换 manifest 后仍可通过解析与目录身份校验 |
| `PackageManager.set_enabled` | 在受管副本中更新启用字段 | 在已登记文件操作范围内完成原子写入 |
| `Registry.set_enabled(package_id, enabled)` | 编排启用或禁用 | 成功返回的 ActivationReport 与 Runtime、Bus 和安装副本一致 |

### 3.2 生命周期与一致性

启动在生成加载计划前补写旧副本，再排除 `enabled == false` 的包。禁用操作先取得包操作和 Runtime 锁，再注销 Handler、释放本包资源并删除 Runtime 生效记录，最后保留目录写入 `false`。启用操作在报告登记后写入 `true`，随后执行正常 plan/apply；加载失败时把字段恢复为 `false`，避免下一次启动导入失败的代码。

重载不改变安装副本的期望状态。已启用包按既有热切换流程重新加载；已禁用包没有可替换的生效记录，因此返回成功的空操作，保持其安装副本和 `enable: false` 不变。

包被其它生效包依赖、存在在途调用或已有管理操作时，禁用与卸载采用相同拒绝规则。安装报告允许“安装成功但未生效”的禁用包状态；它不成为其它包的已满足依赖。

### 3.3 兼容与迁移

`enable` 长期保持可选，不安排升级为必填字段。旧用户来源不被修改；仅受管安装副本在复制或启动扫描时补写默认值。多版本目录仍按既有选版规则处理。

## 5. 风险与已知限制

在同一安装目录中运行的多个 Registry 仍依赖既有安装报告与运行锁协调。启用状态是持久化期望状态，不能终止已进入第三方代码的线程或撤回其外部副作用。
