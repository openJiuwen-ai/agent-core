# Core 开发与文档维护规范

本文适用于 `openjiuwen/core/` 及其全部子目录，规定代码开发、测试验证与设计文档维护方式。
具体接口、状态机和算法在所属模块的实现、测试及设计文档中维护。

## 适用范围与规则入口

- 先遵循[仓库根规则](../../AGENTS.md)，再执行本文；目标子目录的规则补充其职责边界和专属要求。
  修改前检查从 `core/` 到目标文件所在目录的适用规则，不将其他子目录的规则扩大应用。
- 开发前阅读目标模块的实现、公开导出、调用方、相关测试和已有设计，确认本次变化影响哪些行为。
  本文中的目录链接是阅读入口，不代替源码核对。
- 工具版本与配置以 [pyproject.toml](../../pyproject.toml) 为准，常用检查入口以
  [Makefile](../../Makefile) 为准。编码、错误码、日志及提交细则沿用仓库规则。
- Core 共通规则集中维护在本文；确需增加局部约束时，在对应子目录新增 `AGENTS.md` 并说明适用范围。
  同级 `CLAUDE.md` 只保留 `@AGENTS.md` 引用，规则修订写入 `AGENTS.md`。

| [workflow/](workflow/)、[graph/](graph/)、[controller/](controller/)、[operator/](operator/) | 编排、图执行、控制和算子处理；修改时核对调用链、状态推进及输出语义 |

## 代码开发要求

### 公共接口与兼容性

- 将模块 `__init__.py` 导出、已公开文档和示例中的接口视为公共 API；修改时检查定义、重导出和调用方。
  保持已有名称、位置参数及默认行为兼容，新可选参数优先使用仅关键字参数。
- `single_agent/` 是当前单智能体 API；`single_agent/legacy/` 用于兼容维护，新增能力优先基于当前 API。
  兼容调整须核对旧入口和新入口各自的行为。
- 保持 Card 与 Config 的职责分离：Card 描述身份和静态元数据，运行行为及资源归属由配置、实例和管理器承担。
  新增资源能力时，核对 Card 定义、注册、获取与实际执行是否一致。
- API、配置、默认值、异常、事件、流式输出及序列化形态发生变化时，检查消费方和兼容范围。
  需要破坏兼容性时，先明确影响、迁移方式和验证范围，遵循已有授权及适用规则处理。

### 模块边界、状态与资源

- 优先复用现有公共抽象和能力入口，保持修改聚焦；新增依赖前检查模块职责与循环依赖风险。
  跨模块变更核对提供方与消费方，不只修改一端。
- `Runner.resource_mgr` 是进程级共享状态。资源 ID 应稳定且避免冲突；创建、注册、获取和释放的责任必须明确，
  测试须清理自身引入的资源及全局状态，避免相互污染。
- 涉及会话、缓存、持久数据和恢复时，明确作用域、事实来源、保存与清理时机。
  不因能读取历史数据就推断任务能够恢复，也不因使用同一 ID 就假定状态可以安全共享。
- 异步调用中避免引入阻塞；涉及流式输出、取消、中断或异常时，核对任务退出、状态保存和资源释放。
  不吞掉异常或将部分成功、结果未知改写为完整成功。
- 系统操作和安全相关修改须检查校验、权限及副作用发生的顺序，并覆盖适用的拒绝和清理路径。

### 编码与维护

- 沿用目标模块的命名、类型标注和代码组织；新增公共接口补充准确的类型和 docstring。
  导入、格式和静态检查按仓库配置执行，不在本文复制工具参数。
- 日志使用 `common/logging/` 的既有入口；异常和错误码遵循 `common/exception/` 的既有模型及仓库规则。
  不使用 `print()` 代替库日志，不把凭据或敏感业务数据写入日志和示例。
- 重构时检查导出、导入路径、调用方、测试及文档引用；契约保持不变时，也需确认行为未因重构改变。

## 测试与验证

- 优先定位 [Core 单元测试](../../tests/unit_tests/core/) 中对应行为的已有覆盖；测试目录存在历史命名差异，
  不机械地按源码路径推导测试位置。行为变化时补充有价值的回归覆盖。
- 根据变更范围验证正常路径、错误路径及适用的兼容性、状态转换、流式输出、中断、恢复和隔离行为。
  跨模块变化补充协作验证，公共接口变化检查公开入口。
- 单元测试应快速、可重复，隔离外部服务与共享状态。需要真实服务或凭据的验证放在适用的集成或系统测试中，
  按现有标记和环境要求执行。
- 以下命令均在仓库根目录运行；测试路径应替换为实际受影响的文件或目录。

```text
make test TESTFLAGS="tests/unit_tests/core/session/test_session.py"
make check
make type-check
```

`make check` 和 `make type-check` 默认检查已暂存的 Python 文件，可使用 `COMMITS=N` 检查最近提交。
它们不执行测试，也不验证 Markdown 链接；未选中文件不能视为完成检查。检查工具失败时命令应返回非零状态，
记录结果时仍须核对实际选中的文件、各工具输出及退出状态，不能仅凭命令结束判断通过。

Windows 或其他未安装 `make` 的环境可直接使用 `uv run`。检查未暂存或未跟踪的 Python 文件时，
也可直接传入实际文件路径，无需为运行检查修改暂存区；以下示例中的路径均替换为本次受影响的文件：

```text
uv run pytest tests/unit_tests/core/session/test_session.py
uv run ruff check openjiuwen/core/session/session.py
uv run ruff format --check openjiuwen/core/session/session.py
uv run codespell openjiuwen/core/session/session.py
uv run pylint openjiuwen/core/session/session.py
uv run mypy openjiuwen/core/session/session.py
```

上述静态检查对应 `make check` 和 `make type-check` 的工具范围。未安装 `uv` 时，在已安装项目及测试、
检查依赖的 Python 环境中将 `uv run` 替换为 `python -m`；工具缺失或环境错误应记录为未完成验证。

验证记录写明实际范围、环境、命令、结果和未完成项。未执行不能写成通过，模拟验证不能扩大解释为
真实服务或完整业务验证。纯文档修改检查内容、链接和差异，无需仅为文档改动运行业务测试。

## 内容边界与文档分工

`AGENTS.md` 维护开发规则和阅读入口，设计文档维护具体方案与契约。下列路径相对所属文档目录；
Core 共享文档放在 `core/docs/`，模块专属文档可放在对应模块的 `docs/`。除已有 `templates/` 外，
其他目录按实际主题建立，不预建空文件，也不为套用模板创建目录。

| 目录或文档 | 内容归属 | 更新时机 |
| --- | --- | --- |
| `specs/` | 已确认的接口、状态、边界和不变量 | 新契约形成或已有契约变化 |
| `features/` | 一项完整特性或重要重构的背景、方案、取舍、验证与遗留 | 实现前形成方案，开发中补充决策和证据 |
| `designs/` 中的概览、架构 | 整体定位、职责分工、关键流程和设计前提 | 整体设计、模块协作或关键约束变化 |
| `designs/` 中的开发计划 | 工作拆分、依赖、负责人、进度及验收证据 | 多阶段开发或持续协作需要跟踪时 |
| `templates/` | 公共模板及填写、维护规范，在 `core/docs/templates/` 统一维护 | 通用写作要求变化 |

共享契约指定唯一维护位置，模块专属契约由所属模块维护；相关文档通过链接关联。
接口定义、验收标准、完整 Schema 和当前进度分别在其归属文件维护，其他文档只引用必要结论。

### 命名与编号

```text
specs/S_NN_<slug>.md
features/F_NN_<slug>.md
designs/<slug>.md
```

- `NN` 为至少两位的递增序号，超过 99 后自然扩展位数。以同一 `docs/specs/` 或 `docs/features/`
  目录为编号作用域，不跨模块统一编号。新编号取当前文件、目标分支可追溯历史中已用编号及已登记预留编号的
  最大值加一，首次编号从 `01` 开始；不按文件数量计算，不复用已删除编号。历史不全时先补齐相关历史或核对维护记录。
- 并行新增前核对目标分支及已知进行中的变更；需要预留编号时，在已有计划或协作记录中登记编号、文档作用域和负责人，
  不将未登记的本地取号视为独占预留。合并前再次核对；冲突时保留目标分支已有编号，为待合入的新文档重新取号，
  同步文件名、正文及全部引用，不重排已合入文档。仅在并行取号频繁时增加统一预留记录。
- `<slug>` 使用简短英文小写单词，以短横线连接；文件名不带日期。
  已有文件不为统一样式而批量重命名或重排编号，确需移动时修复引用并说明替代关系。
- 日期写入元信息，使用 `YYYY-MM-DD`。Spec 更新最近修订日期；feature 保留归档日期并记录后续修订日期。
  元信息不填需要提交后回填的 commit hash。
- 一项连贯的设计变更归档为一份 feature，不按提交次数拆分；后续修订保留原编号和历史决策。
  过时结论注明适用范围及替代关系，不删除归档来隐藏历史。

### 模板与必要内容

编写或修改相应类型的设计文档前，阅读对应模板的填写与维护要求。章节按实际范围裁剪，
不保留占位内容，也不为模板示例增加系统原本没有的能力或保证。

| 文档类型 | 模板 |
| --- | --- |
| 设计概览 | [overview-template.md](docs/templates/overview-template.md) |
| 架构详细设计 | [architecture-template.md](docs/templates/architecture-template.md) |
| 模块规约 | [spec-template.md](docs/templates/spec-template.md) |
| 特性设计 | [feature-design-template.md](docs/templates/feature-design-template.md) |
| 特性开发计划与进度 | [feature-development-plan-template.md](docs/templates/feature-development-plan-template.md) |

- Spec 明确范围、适用的接口与错误语义、状态及数据生命周期，并用稳定编号列出不变量。
  引用其他 spec 的契约，不复制其定义。
- Feature 解释背景、采用方案、重要备选及放弃原因、契约影响、验证和遗留，不只复述提交记录。
- 区分目标方案、已确认待实现契约、已实现行为和待验证前提。未实现条款注明缺口，
  未确认方案不能写成已生效接口或能力保证。
- 实现路径、符号、默认值和示例应能与代码核对；拟议接口及示意代码明确标注。
  当前契约、历史决策与历史验证结果分别表达。

## 特性设计与契约同步

1. 开发前核对相关设计、契约和实现。新增能力、重要重构或跨模块契约变化时，先在所属文档目录
   新建或更新 feature，说明范围、方案、影响及验证方式，再推进实现。
2. 修复实现使其符合已有契约、契约不变的局部调整和纯文字修改，按实际影响补充回归测试、修正文档或记录验证，
   无需仅因实现行为被纠正而新增 feature、spec 或开发计划。若修复需要重要设计取舍或跨模块重构，按第 1 条建档；
   已有规则和当前任务另有要求时遵循其要求。
3. 预期契约中的 API、配置、错误语义、状态、不变量或职责发生变化时，同步主责 spec 和相关 feature；
   没有主责 spec 时，将需长期维护的新契约建为 spec；没有相关 feature 时，为契约变更新建 feature。
   影响整体设计时同步概览、架构及适用的计划。架构调整按已有授权和适用规则执行，模板不新增审批门槛。
4. 文档与实现不一致时，先区分文档过时、实现缺陷和待实现设计。修正过时事实；实现违背已确认契约时，
   修复实现或明确提出契约调整，不默默降低文档保证来掩盖缺口。
5. 验证后将范围、结果及限制写入 feature 或验证记录；spec 保留契约和验证入口。
   当前实现与待实现目标、单元验证与真实联调分别说明。
6. 用户可见行为变化时，核对仓库 `docs/`、README 及 `examples/` 中受影响的说明与用法，按实际影响同步，
   不以内部 spec 或 feature 的更新代替用户文档维护。

### 开发计划与进度维护

- 多阶段特性或多人协作需要计划时，指定一份开发计划或既有统一进度表维护负责人、状态、依赖和证据。
  概览、架构和 feature 引用该位置，默认不重复填写当前负责人、状态或排期。无独立计划时，可由 feature
  维护本特性的进度和验收依据，并明确其唯一维护位置；后续建立计划时迁移管理字段并保留链接，技术验证记录仍就近维护。
- 新增或调整特性时，更新目标、范围、独立验收标准、必要前置及适用的交付节点；
  同步受影响的依赖、条目和统计。计划条目与 feature 文件编号分别管理，建立明确关联。
- 开工及进展变化时更新负责人、状态、已完成范围、验证结果、证据链接和最近更新；
  阻塞时说明缺口、影响、解除条件及需要谁配合。
- 按约定验收范围判断完成。部分验证通过、代码完成或 PR 合并不能单独代替整项验收；
  真实联调注明环境和对端版本。常规进度只更新计划与证据，不重复改写验收标准。

## 引用与交付检查

- 文档链接从引用所在文件的目录计算。新增、移动或删除文件后，检查相对路径、章节锚点及引用方；
  复制模板时重新计算路径，不直接沿用示例链接。
- 提交方式遵循[仓库 Git 工作流](../../.claude/rules/git-workflow.md)，使用 `type(scope): description`，
  scope 根据实际变更模块选择；有关联 Issue 或 PR 时引用实际编号。
  按逻辑变更组织提交，不强制将实现、测试和文档拆成固定数量的提交。
- 交付前核对代码、公开导出、调用方、测试和文档是否一致，说明已执行验证及剩余限制。
  设计文档检查名称、编号、日期、链接、正文与图表；`CLAUDE.md` 保持引用壳。
- 检查改动范围，分别运行 `git diff --check` 和 `git diff --cached --check`，覆盖未暂存和已暂存差异；
  未跟踪的新文件还需单独检查，因为这两条命令都不覆盖未跟踪文件。
