# 阻塞审计机制改动说明（方案二）

> 供后续评审。说明本次在 `openjiuwen/harness/goal` 子系统实现的**阻塞审计规则**：防止 agent 过早标记 BLOCKED 放弃任务。

## 一、背景

**问题**：goal 模式下，agent 可能遇到第一个阻塞就直接 `submit_goal_report(status=blocked)`，评估器确认后 goal 立即 BLOCKED 收工——**即使换个思路本来能继续**。这导致 agent 过早放弃。

**方案**（对齐 Codex 原版 `continuation.md` 的 Blocked audit——它要求"**the same blocking condition** repeated 3 consecutive turns"，并由模型语义判断"相同"）：

> **相同阻塞条件必须连续出现 N 次（默认 3）才确认 BLOCKED**，前 N-1 次降级为 continue，让 agent 继续尝试。

**实现分工**（用户确认的"机制层计数"）：
- **机制层**（确定性、可单测）：`apply_assessment` 累计连续"相同阻塞"评估，达到阈值才 finalize BLOCKED，否则降级 continue
- **assessor 层**（语义判断）：assessor 看到 `<blocking_history>`，输出 `blocking_same_as_previous` 布尔，机制层据此 +1（相同）或重置（不同）

## 二、改动总览

| 文件 | 改动 |
|------|------|
| `goal/schema.py` | `GoalRecord` 加 `blocking_history: list[str]` + 序列化；`GoalAssessment` 加 `blocking_same_as_previous: Optional[bool]` |
| `goal/evaluation.py` | `_parse_assessment_json` 读 assessor 输出的 `blocking_same_as_previous`（布尔）|
| `goal/manager.py` | `apply_assessment` 阻塞审计计数（同阻塞达阈值才 BLOCKED，否则降级 continue）；`resume` 清空历史；`blocked_threshold` 参数；补终态日志 |
| `prompts/sections/goal.py` | `build_transcript_assessor_prompt` 加 `blocking_history` 参数注入 `<blocking_history>`；系统规则加阻塞审计规则（含 `blocking_same_as_previous` 字段说明）|
| `rails/task_completion_rail.py` | `_invoke_transcript_assessor` 传 `record.blocking_history` |

## 三、详细改动

### 3.1 数据模型（schema.py）

```python
@dataclass
class GoalAssessment:
    status: GoalAssessmentStatus
    evidence: str
    remaining_work: Optional[str] = None
    next_instruction: Optional[str] = None
    blocking_same_as_previous: Optional[bool] = None   # assessor 判"是否与历史同一阻塞"

@dataclass
class GoalRecord:
    ...
    blocking_history: list[str] = field(default_factory=list)  # 连续相同阻塞的累计
```

- `GoalAssessment.from_dict` 只接受真正的 bool（`"string"` / 缺失 → None）
- `GoalRecord.to_dict/from_dict` 保留 `blocking_history`，旧持久化数据无此字段 → 空列表（兼容）

### 3.2 评估器解析（evaluation.py）

`_parse_assessment_json` 读取 `blocking_same_as_previous`（assessor JSON 里的布尔），透传到 `GoalAssessment`。

### 3.3 机制层计数（manager.py · apply_assessment）

```python
elif assessment.status is GoalAssessmentStatus.BLOCKED:
    same = assessment.blocking_same_as_previous
    if same is not False and record.blocking_history:
        record.blocking_history.append(assessment.evidence)   # 相同 → 追加
    else:
        record.blocking_history = [assessment.evidence]       # 不同 → 重置
    if len(record.blocking_history) >= self._blocked_threshold:
        record.status = GoalStatus.BLOCKED                    # 达阈值 → 确认 BLOCKED
        record.last_stop_reason = "blocked"
    else:
        record.status = GoalStatus.ACTIVE                     # 未达阈值 → 降级 continue
        record.last_assessment = GoalAssessment(CONTINUE, ...)
```

- **相同阻塞**（`same is not False`，含 assessor 未给信号的保守情况）→ 追加历史，计数 +1
- **不同阻塞**（`same is False`）→ 重置历史为当前，计数 = 1
- **达到阈值**（`len(blocking_history) >= blocked_threshold`，默认 3）→ 最终 BLOCKED
- **未达阈值** → 保持 ACTIVE，降级为 CONTINUE，`next_instruction` 提示 agent 尝试替代方案
- **非阻塞**（COMPLETE/CONTINUE）→ 清空 `blocking_history`（重新审计）
- **resume**（从 PAUSED/BLOCKED 恢复）→ 清空 `blocking_history`（对齐 Codex "resumed run as fresh blocked audit"）

`blocked_threshold` 是 `GoalManager.__init__` 参数（默认 3），可在 host/测试覆盖。

### 3.4 终态日志（manager.py）

`apply_assessment` 状态应用后补日志，使 goal.log 可见完整终态链路（此前 manager 无日志，终态静默）：

```python
logger.info("[GoalLifecycle] apply assessment: status=%s goal=%s blocking_history_len=%d blocked_threshold=%d", ...)
```

### 3.5 Assessor prompt（prompts/sections/goal.py）

- `build_transcript_assessor_prompt(..., blocking_history=None)`：非空时注入 `<blocking_history>` 块（逐条 `- Attempt N: <evidence>`）
- `TRANSCRIPT_ASSESSOR_SYSTEM`（cn/en）阻塞审计规则：
  - 看过往阻塞；当前阻塞与历史**同一根本原因**时输出 `"blocking_same_as_previous": true`，否则 `false`
  - 系统会累计连续相同阻塞、达阈值才确认 blocked；对真实持续阻塞仍报 blocked（供机制计数），但**不要因难/慢/不确定报 blocked**
  - JSON 字段说明补 `blocking_same_as_previous`（仅 status=blocked 填）

### 3.6 Rail 传历史（task_completion_rail.py）

`_invoke_transcript_assessor` 调 `build_transcript_assessor_prompt` 时传 `blocking_history=record.blocking_history`。

## 六、边界与取舍

- **"同一阻塞"语义**：由 assessor 语义判断 `blocking_same_as_previous`（对齐 Codex）；机制层只读该信号做 +1/重置，不自己比对文本。assessor 未给信号（None）时保守当作"相同"追加，避免误重置导致计数永远到不了阈值。
- **连续计数 vs 总阻塞数**：统计的是"当前这串连续相同阻塞"的长度；遇到不同阻塞重置、非阻塞清空。因此"无token→磁盘满→无token"（总3次但非连续相同）不会误判 BLOCKED。
- **BLOCKED 已确认后**：goal 进入 BLOCKED；用户 resume 才清历史重审（对齐 Codex）。
- **权限阻塞**：web host 下 `bash: ask` 可能让 agent 在做依赖外部命令的任务时卡在权限弹窗（与阻塞审计正交，属权限配置问题，另案处理）。
