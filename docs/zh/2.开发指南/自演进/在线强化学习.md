# Online RL/SFT 后端运行说明

英文版见 [online-rl-service-operations-backends.md](./online-rl-service-operations-backends.md)。

本文补充 [Online RL Service Operations](./online-rl-service-operations.md)，
说明 JiuwenSwarm 注入 Online Rail 后的 RL 和 SFT 链路，以及通过 SWE rollout
skill 收集高质量 SFT 数据的链路。

代码入口位于：

```text
openjiuwen/harness/deep_agent.py
  -> openjiuwen/agent_evolving/agent_rl/online/core/rail_factory.py
```

## 使用前先选择链路

设置环境变量前先确定目标链路。三条链路的数据契约和上传时机不同。

| 目标 | Rail/输出 | 上传时机 | 训练触发方式 |
| --- | --- | --- | --- |
| 通过 PPO 提升在线策略 | `RLOnlineRail` / `rail-v1` | 每个 PPO turn 完成时 | `POST /v1/rl/training/runs` |
| 基于普通 JiuwenSwarm 会话进行 SFT | `SFTOnlineRail` / `sft-raw-v1` 或 `sft-sample-v1` | SFT session flush 时 | SFT-aware Scheduler/launcher |
| 基于已验证 SWE rollout 进行 SFT | `SFTOnlineRail` 加 skill 清洗 / `sft-sample-v1` | 清洗完成且 `resolved=true` 后 | SFT-aware Scheduler/launcher |

## 1. 通用 Rail 注入和边界

`DeepAgent` 创建时会调用
`build_online_training_rail_from_env()`。只有下列开关开启时，才会自动注入 Online
Rail：

```bash
export USE_RL_ONLINE_RAIL=1
```

Rail 工厂按以下规则选择实现：

| 配置 | 注入的 Rail |
| --- | --- |
| `TRAIN_BACKEND=PPO`、`RL` 或 `online_rl` | `RLOnlineRail` |
| `TRAIN_BACKEND=SFT` | `SFTOnlineRail` |
| 未设置 `TRAIN_BACKEND`，且 `RL_ONLINE_CAPTURE_MODE=raw`、`raw_session` 或 `sft_raw` | `SFTOnlineRail` |
| 其他情况 | `RLOnlineRail` |

两种 Rail 均通过 `TrajectoryUploader` 访问：

```text
POST <TRAJECTORY_GATEWAY_URL>/v1/gateway/upload/batch
```

因此，`TRAJECTORY_GATEWAY_URL` 必须从 JiuwenSwarm 所在进程实际可达。Docker、
sidecar 或远端沙箱内不能把宿主机的 `127.0.0.1` 直接当作 Gateway 地址；应使用
宿主机可访问地址、容器网络服务名，或沙箱配置的 upstream 反向代理地址。

主要通用环境变量如下。

| 变量 | 作用 |
| --- | --- |
| `USE_RL_ONLINE_RAIL` | 开启 DeepAgent 的 Online Rail 自动注入。 |
| `TRAIN_BACKEND` | 选择 `PPO`/`RL` 或 `SFT` Rail。 |
| `RL_ONLINE_CAPTURE_MODE` | 兼容模式选择；`raw`、`raw_session`、`sft_raw` 会选择 SFT Rail。 |
| `TRAJECTORY_GATEWAY_URL` | Gateway 地址。 |
| `TRAJECTORY_GATEWAY_API_KEY` | Gateway Bearer Token。 |
| `RL_ONLINE_TENANT_ID` | 轨迹、样本和 LoRA 的稳定租户/用户命名空间。 |
| `LORA_DEFAULT_POLICY` | 设为 `latest_by_user` 时，请求使用该用户当前激活的 LoRA。 |
| `TRAJECTORY_UPLOAD_TIMEOUT_SECONDS` | 上传 HTTP 超时。 |
| `TRAJECTORY_WAL_DIR` | 上传失败时的本地 WAL 目录。 |
| `TRAJECTORY_FORCE_WAL` | 设为 `1` 时仅写 WAL，不实际上传；端到端验证必须保持关闭。 |

当前独立 `online.service` 的 `/v1/rl/training/runs` 运行面固定装配 PPO
executor。它不是通过设置 `TRAIN_BACKEND=SFT` 就自动切换到 SFT 的通用训练
API。SFT 训练应由 SFT-aware 的 Gateway/Scheduler/launcher 调用
`SFTTrainingExecutor`。

### 1.1 部署前检查

启动任一链路前，先确认：

1. 实际运行 JiuwenSwarm 的进程能够访问 `TRAJECTORY_GATEWAY_URL`。
2. `RL_ONLINE_TENANT_ID` 已设置为与目标模型、sample store 和 LoRA repository
   一致的稳定命名空间。
3. Gateway 支持将要上传的协议：PPO 使用 `rail-v1`，SFT 使用
   `sft-raw-v1` 或 `sft-sample-v1`。
4. 除非 rollout 明确将 WAL 用作本地暂存区，否则 `TRAJECTORY_FORCE_WAL` 必须关闭。
5. 训练触发器与样本类型匹配。PPO Training Run 不能消费 SFT 样本，SFT launcher
   也不能消费 `rail-v1` PPO 样本。

## 2. JiuwenSwarm 开启 RL/PPO 训练后端

### 2.1 流程

RL 后端采集的是可用于 PPO 的 turn 级训练样本，不能只保存普通
`prompt`/`response` 文本。

```text
JiuwenSwarm / DeepAgent
  -> RLOnlineRail
  -> 从模型调用和 observability span 采集 messages、token ids、logprobs、usage
  -> rail-v1
  -> TrajectoryUploader
  -> Gateway
  -> Redis pending PPO samples
  -> API 创建 Training Run
  -> PPOTrainingExecutor / veRL-RL
  -> 导出并发布 LoRA
  -> AIGW / 推理服务激活 LoRA
```

`RLOnlineRail` 在调用前为请求补充用户身份和采样需求；调用后从 callback 或
observability span 中恢复模型交换记录。样本至少应包含：

- prompt messages 和 prompt token ids；
- completion token ids；
- 与 completion 对齐的 log probabilities；
- usage、finish reason、模型和会话身份；
- reward 关联所需的 task/session 信息。

Gateway 的 PPO 入口会拒绝缺少 token 或 logprob 真值字段的样本。普通的 SFT
文本对话不能作为 PPO 训练数据使用。

训练任务由 API 显式触发，而不是在每条轨迹上传后隐式训练：

```text
POST /v1/rl/training/runs
  -> 原子 claim 当前 pending 样本批次
  -> PPOTrainingExecutor
  -> PPOBatchEngine / Ray / veRL
  -> checkpoint 和 LoRA
  -> LoRARepository.publish()
  -> AIGWLoRAClient.activate()
```

创建 Training Run 后才上传的新轨迹属于下一批训练，不会混入已 claim 的运行。

### 2.2 最小运行配置

```bash
export USE_RL_ONLINE_RAIL=1
export TRAIN_BACKEND=PPO
export TRAJECTORY_GATEWAY_URL=http://gateway-host:18080
export RL_ONLINE_TENANT_ID=rl-user
export LORA_DEFAULT_POLICY=latest_by_user
export RL_ONLINE_SESSION_DONE_ON_INVOKE_END=1
```

`RL_ONLINE_SESSION_DONE_ON_INVOKE_END=1` 适合按 invoke/turn 采集 PPO 样本。
如果业务需要跨调用累积会话，应由业务回调在完成时显式传递
`session_done`、`close_session` 或 `done`。

### 2.3 RL/PPO 训练资源环境变量

以下变量由 PPO 训练器读取，用于覆盖 YAML 中的训练资源参数：

| 变量 | 作用 |
| --- | --- |
| `ONLINE_RL_VISIBLE_DEVICES_ENV` | 训练设备可见性变量名，默认 `CUDA_VISIBLE_DEVICES`；Ascend 可设为实际 NPU 变量名。 |
| `ONLINE_RL_DEVICE_BACKEND` | 设置为 `ascend`/`npu` 时选择 NPU 路径。 |
| `ONLINE_RL_INIT_LORA_ADAPTER_PATH` | 指定初始 LoRA adapter。 |
| `ONLINE_RL_MAX_PROMPT_LENGTH` | PPO 最大 prompt token 数。 |
| `ONLINE_RL_MAX_RESPONSE_LENGTH` | PPO 最大 completion token 数。 |
| `ONLINE_RL_TRAIN_BATCH_SIZE` | PPO train batch size。 |
| `ONLINE_RL_PPO_MINI_BATCH_SIZE` | PPO mini batch size。 |
| `ONLINE_RL_PPO_MICRO_BATCH_SIZE_PER_GPU` | 每卡 micro batch size。 |
| `ONLINE_RL_SEQUENCE_PARALLEL_SIZE` | sequence/tensor parallel size。 |
| `ONLINE_RL_ACTOR_PPO_MAX_TOKEN_LEN_PER_GPU` | actor 每卡 token 上限。 |
| `ONLINE_RL_ROLLOUT_MAX_MODEL_LEN` | rollout 最大上下文长度。 |
| `ONLINE_RL_ROLLOUT_GPU_MEMORY_UTILIZATION` | rollout 侧显存利用率。 |
| `ONLINE_RL_ACTOR_LEARNING_RATE` | actor 学习率。 |

模型路径、Redis、LoRA repository、训练卡、最小样本数和 AIGW endpoint 等服务级
配置仍由 `RL_SERVICE_CONFIG` 指向的 YAML 管理。

## 3. JiuwenSwarm 开启 SFT 训练后端

### 3.1 流程

SFT 后端以 OpenAI 风格的结构化 `messages`、tool calls 和 assistant 输出作为
主要数据，而不是将整段会话拼接为一个字符串。

```text
JiuwenSwarm / DeepAgent
  -> SFTOnlineRail
  -> 收集结构化 messages、tool calls、assistant response 和任务 metadata
  -> session flush
  -> TrajectoryUploader 直接上传 Gateway
  -> GatewayTrajectoryRuntime
  -> sft-raw-v1    -> SFT raw store    -> SFT rollouter -> sft-sample-v1
  -> sft-sample-v1 -> SFT sample store
  -> SFTTrainingExecutor / veRL SFT
  -> LoRARepository.publish()
```

这里的“直接上传”指 `SFTOnlineRail` 在 session flush 后直接调用 Gateway，不经
PPO 的 reward/trajectory 训练链路。Gateway 必须把 SFT 协议交给
`GatewayTrajectoryRuntime.record_sft_raw()` 或
`GatewayTrajectoryRuntime.record_sft_sample()`：

- `sft-raw-v1` 存入 SFT raw store；
- `sft-sample-v1` 存入可训练的 SFT sample store。

当前独立 `online.service` 中的 `/v1/gateway/upload/batch` 主要面向 `rail-v1`
的 PPO ingestion。部署 SFT 时，应确认实际对外 Gateway 已接入上述 SFT runtime
入口，不能仅以 PPO route 可用推断 SFT raw/sample 已正确落库。

具体而言，当前独立 route 调用的是
`trajectory_api.rail_ingestor.ingest_rail_batch(payload)`。虽然
`GatewayTrajectoryRuntime.batch_create_trajectories()` 支持 SFT 协议，但该
方法没有被这个独立 route 调用。对外 Gateway 必须显式完成协议分发。

### 3.2 上传模式和 flush 规则

| `SFT_ONLINE_UPLOAD_MODE` | Gateway 中的数据 | 适用场景 |
| --- | --- | --- |
| `raw` | `sft-raw-v1` | 保留原始会话，后续由 supervisor/replay rollouter 生成教师答案。 |
| `sample` | `sft-sample-v1` | 当前调用已经产生可训练的 assistant 教师答案，可直接进入 SFT sample store。 |

SFT 的会话 flush 规则如下：

| 条件 | 行为 |
| --- | --- |
| `RL_ONLINE_SESSION_DONE_ON_INVOKE_END=1` | 每次 invoke 结束时上传当前会话。 |
| callback context 中有 `session_done`、`close_session` 或 `done` | 显式结束并上传会话。 |
| `TRAJECTORY_SESSION_FLUSH_TOKEN_THRESHOLD_K>0` 且达到阈值 | 按 token 阈值 flush。 |

普通 SFT 会话默认不会在每次 invoke 后结束，可跨多轮累积。若设
`RL_ONLINE_SESSION_DONE_ON_INVOKE_END=1`，多轮业务请求会产生多条独立上传
记录，而不是一条完整多轮 session。

### 3.3 最小运行配置

直接上传 raw session：

```bash
export USE_RL_ONLINE_RAIL=1
export TRAIN_BACKEND=SFT
export SFT_ONLINE_UPLOAD_MODE=raw
export TRAJECTORY_GATEWAY_URL=http://gateway-host:18080
export RL_ONLINE_TENANT_ID=sft-user
export SFT_SCENARIO=multi_turn_supervisor
export SFT_TASK_PROMPT="implement the requested change"
```

直接上传可训练 sample：

```bash
export USE_RL_ONLINE_RAIL=1
export TRAIN_BACKEND=SFT
export SFT_ONLINE_UPLOAD_MODE=sample
export TRAJECTORY_GATEWAY_URL=http://gateway-host:18080
export RL_ONLINE_TENANT_ID=sft-user
export RL_ONLINE_SESSION_DONE_ON_INVOKE_END=1
```

### 3.4 SFT 主要环境变量

| 变量 | 作用 |
| --- | --- |
| `SFT_ONLINE_UPLOAD_MODE` | 选择 `raw` 或 `sample` 上传协议。 |
| `SFT_SCENARIO` | 标记 SFT 数据来源或场景，例如 `multi_turn_supervisor`。 |
| `SFT_TASK_PROMPT` | 任务 prompt metadata。 |
| `SFT_INSTANCE_ID` | SWE 或数据集 case ID。 |
| `SFT_DOCKER_IMAGE` | 当前任务镜像 metadata。 |
| `SFT_DATASET_CASE_JSON` | 任务 case JSON metadata。 |
| `SFT_WORKSPACE_REF_JSON` | workspace/repository metadata。 |
| `SFT_SUPERVISOR_TIMEOUT` | supervisor 调用 timeout。 |
| `SFT_TASK_UPLOAD_SETTLE_SECONDS` | 任务完成后等待异步上传完成的秒数。 |
| `SFT_ROLLOUT_CONCURRENCY` | supervisor/task rollout 并发数。 |
| `SFT_VERL_MAX_LENGTH` | SFT 最大训练序列长度。 |
| `SFT_VERL_TRUNCATION` | 超长样本截断方向。 |
| `SFT_VERL_WINDOW_LENGTH` | 大于 0 时按 turn 生成滑动窗口。 |
| `SFT_VERL_WINDOW_OVERLAP_TURNS` | 相邻窗口的 turn 重叠数。 |
| `SFT_VERL_SUPERVISE` | 监督范围，例如 `last` 或全部 assistant turn。 |
| `SFT_VERL_TRAIN_BATCH_SIZE` | SFT train batch size。 |
| `SFT_VERL_MICRO_BATCH_SIZE_PER_GPU` | 每卡 SFT micro batch size。 |
| `SFT_VERL_LORA_RANK` | LoRA rank。 |
| `SFT_VERL_LORA_ALPHA` | LoRA alpha。 |
| `SFT_VERL_TARGET_MODULES` | LoRA target modules。 |
| `SFT_VERL_DEVICE` | veRL SFT device，例如 `cuda` 或 `npu`。 |
| `SFT_VERL_NNODES`、`SFT_VERL_NODE_RANK`、`SFT_VERL_MASTER_ADDR`、`SFT_VERL_MASTER_PORT` | 多节点 torchrun 配置。 |

SFT trainer 与 PPO trainer 共用 `ONLINE_RL_VISIBLE_DEVICES_ENV`。例如 Ascend
环境可按实际运行时使用的 NPU 可见卡变量配置：

```bash
export ONLINE_RL_VISIBLE_DEVICES_ENV=ASCEND_RT_VISIBLE_DEVICES
export SFT_VERL_DEVICE=npu
```

## 4. 使用 SWE rollout skill 进行 SFT 微调

### 4.1 链路目标

SWE rollout skill 用于把 SWE case 重放为可验证的 supervisor 轨迹，再把通过
评估的数据交给 SFT。该链路的质量门禁是：**只有 `resolved=true` 的用例可上传到
Gateway 并进入训练集**。

```text
SWE dataset mapping
  -> rollout skill 读取 case、镜像和 commit 信息
  -> 为每个 case 启动独立 rollout 环境
  -> JiuwenSwarm 使用 Supervisor 模型完成任务
  -> 收集会话、工具调用、补丁和执行结果
  -> 数据清洗与 case evaluator
  -> resolved=true
  -> 规范化为 sft-sample-v1
  -> Gateway / RedisSFTStore
  -> API 触发 SFT 训练
  -> veRL SFT 导出 LoRA
```

`resolved=false`、超时、启动失败、轨迹不完整、无法解析 assistant 消息或清洗失败的
case 只能记录诊断日志或保存为排障 artifact，不能进入 SFT sample store，也不能被
本次训练 claim。

### 4.2 数据清洗和质量门禁

skill 在上传前至少完成以下处理：

1. 依据 dataset mapping 读取 case 的 instance ID、repo、base commit、任务描述和
   测试信息。
2. 收集 supervisor 的结构化 messages、tool calls、assistant 最终输出、改动和
   验证结果。
3. 删除运行控制日志、容器启动日志、密钥、无关 stdout/stderr 和无法表示为消息的
   内容。
4. 规范化为 OpenAI 风格 roles/content/tool calls，保留稳定的
   `user_id`、`session_id`、`instance_id` 和模型信息。
5. 校验存在可监督的 assistant 内容，并按目标 tokenizer 和
   `SFT_VERL_MAX_LENGTH` 进行长度统计、截断或跳过记录。
6. 执行 case evaluator，只有评估结果明确为 `resolved=true` 时生成
   `sft-sample-v1` 并上传。

这条链路不能在 evaluator 返回结果前上传。rollout 采集阶段必须关闭所有 flush
触发条件：

```bash
export RL_ONLINE_SESSION_DONE_ON_INVOKE_END=0
export TRAJECTORY_SESSION_FLUSH_TOKEN_THRESHOLD_K=0
```

skill 在评估完成前还不能向 JiuwenSwarm 传递 `session_done`、`close_session`
或 `done`。即使 `RL_ONLINE_SESSION_DONE_ON_INVOKE_END=0`，这些 callback 值
也会让 `SFTOnlineRail` 显式 flush。

当前 Docker task-rollout 默认同时设置
`RL_ONLINE_SESSION_DONE_ON_INVOKE_END=1`，并以 `session_done=True`、
`close_session=True` 结束 chat 请求。按该默认配置运行时，每个完成的 rollout
都会在评估前上传，因此**不满足仅 resolved 上传**的要求。SWE skill 必须覆盖该
环境和完成行为，或者使用 WAL 等本地暂存机制，在评估完成后仅上传通过的 payload。

在 evaluator 判定 `resolved=true` 且清洗成功后，skill 才通过显式 session 完成
信号或 Gateway client 上传最终 `sft-sample-v1`。未通过 case 既不能 flush 到
Gateway，也不能发送直接上传请求。

### 4.3 Supervisor 与 rollout 环境变量

rollout 中的 JiuwenSwarm 应使用 supervisor 模型，而非业务 Agent 默认模型。
通常由 skill 在子进程中设置：

| 变量 | 作用 |
| --- | --- |
| `SUPERVISOR_URL` | Supervisor 的 OpenAI-compatible endpoint。 |
| `SUPERVISOR_TOKEN` | Supervisor 认证 token。 |
| `SUPERVISOR_MODEL` | Supervisor 模型名。 |
| `API_BASE` | JiuwenSwarm 实际访问的模型地址，通常由 skill 设置为 `SUPERVISOR_URL` 对应入口。 |
| `API_KEY` | JiuwenSwarm 实际使用的模型 token，通常来自 `SUPERVISOR_TOKEN`。 |
| `MODEL_NAME` | JiuwenSwarm 实际使用的模型名，通常来自 `SUPERVISOR_MODEL`。 |
| `SFT_ROLLOUT_CONCURRENCY` | 同时重放的 case 数。 |
| `SFT_DOCKER_ROLLOUT_TIMEOUT` | 单 case Docker/SWE rollout timeout。 |
| `SFT_DOCKER_ROLLOUT_COMMAND` | 容器内执行 JiuwenSwarm 任务的命令。 |
| `SFT_DOCKER_ROLLOUT_DEBUG_LOG` | 是否输出 rollout stdout/stderr。 |
| `SFT_TASK_CWD` | JiuwenSwarm 处理 case 时的工作目录。 |
| `SFT_TASK_MODE` | JiuwenSwarm 的任务模式。 |
| `SFT_TASK_MAX_ITERATIONS` | 单任务最大迭代数。 |
| `SFT_TASK_CHAT_TIMEOUT` | 单任务聊天完成 timeout。 |
| `SFT_LOCAL_REPO_WORK_ROOT` | local_program rollout 的工作目录根路径。 |
| `SFT_LOCAL_PROGRAM_SOURCE_DIR` | local_program 题目/源码目录。 |

无论 rollout 运行在 Docker、local_program、sidecar 还是远端 sandbox 中，
以下配置必须在实际执行 JiuwenSwarm 的进程中生效：

```bash
export USE_RL_ONLINE_RAIL=1
export TRAIN_BACKEND=SFT
export SFT_ONLINE_UPLOAD_MODE=sample
export TRAJECTORY_GATEWAY_URL=http://gateway-reachable-from-rollout:18080
export RL_ONLINE_TENANT_ID=<stable-training-user>
export RL_ONLINE_SESSION_DONE_ON_INVOKE_END=0
export TRAJECTORY_SESSION_FLUSH_TOKEN_THRESHOLD_K=0
```

### 4.4 训练触发和验收

SWE skill 负责采集、清洗、评估和上传；训练仍由 API 显式触发。调用训练 API 前，
应确认：

1. Gateway 已收到预期数量的 `sft-sample-v1`；
2. 所有将参与本次训练的样本都来自 `resolved=true` 的 case；
3. `user_id`、目标模型和 LoRA namespace 与训练请求一致；
4. SFT scheduler/launcher 已选择 `SFTTrainingExecutor`，而非 PPO executor；
5. tokenizer 使用实际训练的 `base_model_path`；
6. `SFT_VERL_MAX_LENGTH`、sequence parallel 和 micro batch 与可用显存/NPU
   内存相匹配。

训练完成后至少验证 checkpoint、合并后的 LoRA adapter、LoRA repository 元数据和
推理服务加载状态。仅看到 Gateway 接收到轨迹，不能说明 SFT 训练或 LoRA 发布已经
完成。

## 5. 排障检查

### 5.1 Rail 未注入

检查：

```bash
echo "$USE_RL_ONLINE_RAIL"
echo "$TRAIN_BACKEND"
python -c \
  "from openjiuwen.agent_evolving.agent_rl.online.core.rail_factory import build_online_training_rail_from_env"
```

确认 `USE_RL_ONLINE_RAIL=1`，并明确设置 `TRAIN_BACKEND=PPO` 或
`TRAIN_BACKEND=SFT`。

### 5.2 轨迹未上传

按以下顺序检查：

1. 在 rollout/container/sandbox 内 `curl` 实际的 `TRAJECTORY_GATEWAY_URL`；
2. 确认没有设置 `TRAJECTORY_FORCE_WAL=1`；
3. 检查 `TRAJECTORY_WAL_DIR` 是否存在失败上传记录；
4. RL 检查 token ids 和 logprobs 是否齐全；
5. SFT 检查 Gateway 是否已接入 `record_sft_raw()` 或 `record_sft_sample()`；
6. 普通 SFT 检查 flush 条件；SWE skill 则确认 evaluator 返回
   `resolved=true` 前，自动和显式 flush 条件都保持关闭；
7. 检查 `RL_ONLINE_TENANT_ID` 是否稳定且非空。

### 5.3 SFT 样本存在但训练未启动

确认训练请求不是发送给仅装配 PPO executor 的独立 RL Service；还应检查：

1. SFT sample store 中存在 `pending` 的 `sft-sample-v1`；
2. SFT scheduler/launcher 已使用 SFT backend；
3. `base_model_path` 和 tokenizer 指向同一目标模型；
4. veRL Python 环境、训练设备变量和分布式变量一致；
5. 超长样本的截断/跳过日志符合预期。
