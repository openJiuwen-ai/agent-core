# 上下文引擎

上下文引擎（`ContextEngine`）是 openJiuwen 中用于**模型输入上下文**构建与复用的统一组件。它是 **Agent 层面的成员**，由 Agent 在初始化时创建并持有，围绕 `Session` 和 `ModelContext` 工作，负责：

- 历史对话消息（短期记忆、窗口裁剪）
- Token 统计与窗口控制
- 多个「上下文 ID」并存的场景（例如一个会话里同时跑多条子任务）

## 核心概念

- **ContextEngine**：
  - 入口类：`openjiuwen.core.context_engine.ContextEngine`。
  - 作为 **Agent 的成员**，在 Agent 初始化时创建。
  - 负责按 `session_id + context_id` 管理多个 `ModelContext` 实例。
  - 提供统一的 `create_context / get_context / clear_context / save_contexts` 能力。
- **ModelContext**：
  - 代表**某个会话中的一个具体「对话上下文」**。
  - 负责维护消息列表、构造窗口（`get_context_window()`）等。
- **ContextWindow**：
  - 表示即将送入模型的一次「上下文窗口」快照，即 `get_context_window()` 的返回结果。
  - 封装三类内容：system_messages（系统指令）、context_messages（对话历史）、tools（工具定义）。

## Agent 使用上下文

ContextEngine 是 Agent 的成员，在 Agent 初始化时创建。Agent 在 `invoke` 中通过 `context_engine` 管理上下文，典型流程如下：

### 典型调用流程

1. **Agent 初始化**：创建并持有 `context_engine` 实例（如 `ContextEngine(ContextEngineConfig())`）。
2. **invoke 开始**：调用 `context_engine.create_context(session=agent_session)`，建立当前会话的上下文环境。
3. **invoke 执行**：将请求委托给 Controller（如 ReActController、WorkflowController），Controller 内部按需使用 context。
4. **invoke 结束**：调用 `context_engine.save_contexts(session)` 持久化上下文，并在适当时机 `clear_context` 释放资源。

### 代码示例：Agent 中的上下文使用

```python
# Agent 初始化时（以 BaseAgent / ReActAgent 等为例）
from openjiuwen.core.context_engine import ContextEngine, ContextEngineConfig

class MyAgent(BaseAgent):
    def __init__(self, config):
        super().__init__(config)
        # ContextEngine 由基类或子类在初始化时创建
        self.context_engine = ContextEngine(config=ContextEngineConfig(
            default_window_message_num=100,
        ))

# Agent invoke 中（示意）
async def invoke(self, inputs: Dict, session: Session = None) -> Dict:
    agent_session = session or await self._session.pre_run(session_id=...)
    # 1. 建立上下文环境
    await self.context_engine.create_context(session=agent_session)
    try:
        # 2. 委托给 Controller 执行
        result = await self.controller.invoke(inputs, agent_session)
        # 3. 持久化上下文
        await self.context_engine.save_contexts(agent_session)
        return result
    finally:
        await agent_session.post_run()
```

**要点说明：**

- ContextEngine 由 Agent 创建并持有，不推荐在工作流组件或外部单独创建全局实例。
- `create_context`、`save_contexts` 在 Agent 的 `invoke` 入口统一调用，确保会话隔离与生命周期一致。

## Workflow 使用上下文

Workflow 执行发生在 **Agent 的 invoke 内部**，由 Controller（如 WorkflowController、LLMController）调度。Workflow 使用的 `ModelContext` 由 **Agent 的 context_engine** 创建，并通过 `Runner.run_workflow` 透传，而不是由 Workflow 组件自行创建。

### 典型调用流程

1. Agent 的 `invoke` 将请求委托给 Controller。
2. Controller 在需要执行 Workflow 时，通过 **Agent 的 context_engine** 创建 ModelContext：
   - `context = await self._context_engine.create_context(context_id=workflow_id, session=session)`
3. 将 `context` 透传给 `Runner.run_workflow`：
   - `await Runner.run_workflow(workflow, inputs=..., session=workflow_session, context=context)`
4. Runner 将 `context` 传给 `workflow.invoke(..., context=context)`，Workflow 内部组件即可使用该 context。

### 代码示例：Controller 中创建 context 并透传

```python
# 在 WorkflowController / LLMController 等 Controller 的 invoke 逻辑中
from openjiuwen.core.runner import Runner

# 执行 Workflow 时，通过 Agent 的 context_engine 创建 context，并透传给 Runner
result = await Runner.run_workflow(
    workflow,
    inputs=task.input.arguments,
    session=workflow_session,
    context=await self._context_engine.create_context(
        context_id=workflow_id,
        session=session,
    ),
)
```

### 代码示例：Workflow 组件中接收并使用 context

```python
# Workflow 组件从 invoke 参数中接收 context，无需自行创建
from openjiuwen.core.workflow import WorkflowComponent
from openjiuwen.core.context_engine import ModelContext
from openjiuwen.core.graph.executable import Input, Output
from openjiuwen.core.foundation.llm import UserMessage


class ChatNode(WorkflowComponent):
    async def invoke(self, inputs: Input, session, context: ModelContext) -> Output:
        user_query = inputs.get("query", "")

        # 1. context 由 Agent 透传，直接使用
        await context.add_messages(UserMessage(content=user_query))

        # 2. 构造用于调用大模型的窗口
        window = await context.get_context_window()
        messages = window.get_messages()

        # 3. 调用 Model 完成推理（此处省略）
        # llm_response = await model.ainvoke(messages=messages, ...)

        return {"answer": "..."}
```

**要点说明：**

- Workflow 使用的 context 由 Agent 的 `context_engine.create_context` 创建，经 `Runner.run_workflow` 透传。
- Workflow 组件的 `invoke` 签名中应包含 `context: ModelContext` 参数，由框架注入，**组件不应自行调用 `context_engine.create_context`**。

## 清理与生命周期管理

在长时间运行的服务中，需要考虑上下文的生命周期管理：

- 使用 `clear_context(session_id=...)`：清理某个会话下所有上下文（例如用户主动结束会话时）。
- 使用 `clear_context(session_id=..., context_id=...)`：只清理某个子对话。
- 在 Runner / 服务关闭前，可以选择调用 `save_contexts` + `clear_context`，将必要的信息落盘后释放内存。

示例：

```python
# 用户结束会话时
context_engine.clear_context(session_id="s1")

# 仅结束某个子对话
context_engine.clear_context(session_id="s1", context_id="chat")
```

## 上下文处理器（Processor）

ContextEngine 通过**上下文处理器（Context Processor）**在消息进入上下文或上下文窗口物化时介入，实现对话压缩、消息卸载等容量管理策略。处理器是可插拔的——内置一组处理器，也支持自定义注册。

### 处理器基类与生命周期

所有处理器继承 `ContextProcessor`（`openjiuwen.core.context_engine.processor.base.ContextProcessor`），构造时接收一个 Pydantic 配置：

```python
class ContextProcessor(metaclass=MetaContextProcessor):
    def __init__(self, config: BaseModel): ...
```

处理器可在两个生命周期点介入，每点由一对协程构成（先 `trigger_*` 判断是否介入，再 `on_*` 执行介入）：

| 生命周期点 | 触发判断 | 执行介入 |
|---|---|---|
| 新消息即将加入上下文 | `trigger_add_messages` | `on_add_messages` |
| 上下文窗口物化（`get_context_window`） | `trigger_get_context_window` | `on_get_context_window` |

此外，`ContextProcessor` 提供了 `load_state` / `save_state`（默认空实现，用于跨会话检查点恢复）、`offload_messages`（将消息转存到内存或文件系统）等通用方法，以及 `processor_type()`（返回类名）与 `config` 属性。

### 注册处理器

处理器通过 `ContextEngine.register_processor` 装饰器注册到引擎的处理器映射表，运行时由引擎按 `processor_type()` 实例化：

```python
from openjiuwen.core.context_engine.context_engine import ContextEngine
from openjiuwen.core.context_engine.processor.base import ContextProcessor

@ContextEngine.register_processor()
class MyProcessor(ContextProcessor):
    def __init__(self, config):
        super().__init__(config)
    # 实现 trigger_* / on_* ...
```

### 内置处理器

openJiuwen 内置 10 个处理器，分为**压缩器（Compressor）**与**卸载器（Offloader）**两类，源码位于 `openjiuwen/core/context_engine/processor/`（`compressor/` 与 `offloader/` 两个子目录）。

#### 压缩器（Compressor）

将多轮/整段对话压缩为摘要或结构化记忆块，由 token 或消息数阈值触发。

| 处理器 | 说明 |
|---|---|
| `CurrentRoundCompressor` | 将当前轮对话压缩为协议化的「历史记忆块」，使后续模型将其视为历史记忆而非新指令。 |
| `DialogueCompressor` | 多块对话压缩器，由消息数或 token 阈值触发，调用 LLM 生成 JSON 结构化替换块（含兜底替换路径）。 |
| `RoundLevelCompressor` | 多轮次级压缩器，当上下文 token 达到模型上限比例时触发，将完整 API 轮压缩至目标 token 预算。 |
| `FullCompactProcessor` | 兜底全量压缩器，对齐 Claude Code 的 full compact 流程，生成压缩摘要 + 状态重注入（skills/task-status/plan-mode）+ 最近消息窗口。 |
| `MicroCompactProcessor` | 当某工具累计结果超过阈值时，清除较早的工具结果内容至 `cleared_marker`，仅保留最近若干条。 |
| `ReasoningToolLoopCompactProcessor` | 折叠连续相同的 reasoning/tool 或 tool/args 轮，删除重复轮并插入一条警告消息。 |

#### 卸载器（Offloader）

将超大消息或工具结果转存到内存或文件系统，仅保留精简内容在上下文中。

| 处理器 | 说明 |
|---|---|
| `MessageOffloader` | 卸载器基类，当消息数或 token 超阈值时裁剪超大消息内容并持久化完整内容。 |
| `MessageSummaryOffloader` | 逐条触发的 LLM 摘要卸载器，对新加入的大消息结合任务上下文做摘要，上下文溢出时回退到截断内容。 |
| `ToolResultBudgetProcessor` | 按轮将工具结果裁剪至 token 预算内，卸载被裁剪的剩余部分。 |
| `ToolResultWindowProcessor` | 卸载匹配白名单工具的较早结果，仅保留最近 `keep_last_k` 条在上下文中。 |

> 卸载器之间存在继承关系：`MessageSummaryOffloader` 继承 `MessageOffloader`；`ToolResultBudgetProcessor` 继承 `MessageOffloader`；`ToolResultWindowProcessor` 继承 `ToolResultBudgetProcessor`。

### forked 处理器（重构版）

`openjiuwen/core/context_engine/processor/forked/` 下存在一组同名重构版处理器（`MessageSummaryOffloader`、`DialogueCompressor`、`CurrentRoundCompressor`、`RoundLevelCompressor`、`SessionMemoryCompressor`）。通过 `forked.activate()` 可用重构版**同名覆盖**处理器注册表；DeepAgent 的 `ContextProcessorRail`（priority=85）默认执行该激活，因此 harness 场景下实际运行的是 forked 实现。

forked 版与原版在**压缩落盘能力**上差异显著：

| 落盘链路 | 原版 `processor/` | forked `processor/forked/` |
|---|---|---|
| Offload 落盘（原文卸载到文件） | 有 | 有（写文件失败时保留原消息，不降级） |
| Compression dump（压缩留痕） | 无 | 有（`PrefixCompactProcessor` 统一实现） |
| Compression recall 归档（可回读） | 无 | 有（含 BM25 回读闭环） |
| Debug JSONL / 规则压缩 dump | 无 | 有 |

forked 内部的落盘覆盖情况：

- `RoundLevelCompressor` / `CurrentRoundCompressor` / `DialogueCompressor` 继承 `PrefixCompactProcessor`，自动获得 compression dump 与 recall 归档两条落盘链路。
- `MessageSummaryOffloader` 使用 offload 落盘 + 规则压缩 dump + debug 日志三条链路。
- `SessionMemoryCompressor` 不继承 `PrefixCompactProcessor`，仅有 debug JSONL 落盘。
- 两版 `offload_messages` 行为差异：原版写文件失败会回退到 in_memory 卸载；forked 版失败返回 `None`（调用方保留原消息在上下文中），且落盘文件名带 `processor_type` 前缀。

`PrefixCompactProcessorConfig`（三个 LLM 压缩器共用）还提供两个可选的触发/目标控制字段：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `trigger_token_threshold` | `int \| None` | `None` | 绝对 Token 触发阈值；填写后优先于 `trigger_context_ratio`，上下文（含 system + tools + 消息）达该值才压缩 |
| `target_retention_ratio` | `float \| None` | `None` | 压缩目标保留率；填写后压缩摘要目标 ≈ 被压缩内容 token × 该比例（如 `0.3` = 保留 30%），通过给压缩模型追加长度指令并设置 `max_tokens` 上限实现；`None` 不控制输出长度 |

两个字段均默认 `None`，不填时行为与旧版本完全一致。

## 上下文压缩落盘机制

压缩 / 卸载过程中的落盘分为**功能数据**（丢失会影响回读）与**诊断数据**（opt-in，异常全部吞掉，绝不阻塞压缩主流程）两类，共四条独立链路，统一写入 `{workspace_dir}/context/{session_id}_context/` 目录。

### 目录全景

```
{workspace_dir}/context/{session_id}_context/
├── offload/                      # 卸载原文（功能数据，可回读）
├── compression_recall/           # 压缩归档（功能数据，可回读）
├── compression_logs/             # 压缩留痕（诊断）
├── context_debug/                # 处理器事件流（诊断）
├── message_offloader_debug_logs/ # offloader 诊断
└── rule_compression_dumps/       # 规则压缩诊断
```

> 注意：recall 归档的会话目录名与其它子树不同，为 `{safe(session_id)}-{sha256(session_id)[:12]}_context`（防碰撞），其余子树为 `{session_id}_context`。

### 链路一：Offload 落盘（原文卸载）

`ContextProcessor.offload_messages`（`processor/forked/base.py`）将超大工具消息的完整原文写入文件系统：

- **落盘路径**：`{workspace}/context/{session_id}_context/offload/{processor_type}_{handle}.json`，内容为原始消息 `model_dump()` 后的 JSON。
- **压缩策略**：`rule_then_truncate` —— 先走规则压缩（git diff / HTML / JSON 数组 / 日志 / 搜索结果五类），无收益再降级为头尾各 2000 字符的截断预览。
- **写路径降级链**：优先 `sys_operation.fs().write_file()`（沙箱内），无 sys_operation 时直接 `os` 写（仅限绝对路径），失败返回 `None`、原消息保留在上下文中。
- **回读机制**：上下文中保留的是 `OffloadToolMessage`（`OffloadMixin` 携带 `offload_handle` / `offload_type`），内容尾部附 `[[OFFLOAD: handle=..., type=filesystem, path=...]]` 标记，供 reload 工具按需取回。

### 链路二：Compression Recall 归档（可回溯记忆）

当 `ContextEngineConfig.compression_recall_config.enabled` 开启时，`PrefixCompactProcessor` 在压缩丢弃消息前先归档（`recall/archive.py`）：

- **落盘结构**（每次压缩一个目录，临时目录写完后 `os.replace()` 原子提交）：

```
compression_recall/{memory_id}_{query_slug}/
├── manifest.json     # schema_version / session_id / processor_type 等
├── turns.jsonl       # 按"真实用户消息"分组的 turn 索引
├── raw_messages.json # 原始消息
└── chunks/           # 按 token 切块的 Markdown（默认 3000 / 重叠 300）
```

- **回滚一致性**：压缩被判为"无 token 收益"时删除归档目录回滚。
- **安全设计**：目录名带 `sha256(session_id)[:12]`；逐级 symlink 检查；`resolve().relative_to(workspace)` 防路径逃逸；manifest 校验 session 归属；`memory_id` 正则白名单。
- **回读闭环**：压缩摘要内嵌 `[[COMPRESSION_RECALL: id={memory_id}]]` 标记 → 模型调用 `recall_compressed_context` 工具（`harness/tools/compression_recall.py`）→ BM25 两阶段检索（turn 级 top-2 → chunk 级 top-2）→ token 预算封顶（默认 8000，可由 `OPENJIUWEN_RECALL_MAX_CONTENT_TOKENS` 覆盖）返回。
- 归档动作用 `asyncio.to_thread` 包裹，避免阻塞事件循环。

### 链路三：Compression Dump（压缩留痕）

`compressor/support/compression_dump.py`，由 `PrefixCompactProcessor.on_get_context_window` 成功压缩后调用：

- **开关**：`enable_compression_dump`（默认关闭，零开销）。
- **目录解析顺序**：`config.compression_dump_dir` → 环境变量 `OPENJIUWEN_COMPRESSION_DUMP_DIR` → `{workspace}/context/{session_id}_context/compression_logs/`（均支持 `{session_id}` / `{context_id}` 模板占位符）。
- **落盘内容**：完整证据链 —— 触发指标（context_max、压缩前后 token）、span 三段切分、发给压缩模型的 prompt + 消息 + tools、模型原始响应、提取的摘要、压缩后上下文、token 收益比；文件名为 `{毫秒时间戳}_{processor_type}_{session_id}.json`。

### 链路四：Debug JSONL 追踪（过程诊断）

三处实现，格式统一为逐条 append 的 JSONL：

| 来源 | 目录 | 内容 |
|---|---|---|
| `support/context_debug.py::write_debug_record` | `context_debug/{processor}.jsonl` | threshold_check、span_built、compression_retry 等阶段事件 |
| `MessageSummaryOffloader._write_debug_log` | `message_offloader_debug_logs/` | 触发/跳过原因、原始内容、offload 结果 |
| `RuleCompressionPipeline._dump_result` | `rule_compression_dumps/` | 规则压缩前后对照，路径写入消息 metadata |

### 配置开关汇总

| 链路 | 开关 | 环境变量 | 默认 |
|---|---|---|---|
| Offload 落盘 | 自动（无需开启） | - | 开 |
| Compression dump | `enable_compression_dump` | `OPENJIUWEN_COMPRESSION_DUMP_DIR` | 关 |
| Recall 归档 | `compression_recall_config.enabled` | - | 关 |
| Context debug | `enable_context_debug` / `enable_compression_dump` | `OPENJIUWEN_CONTEXT_DEBUG_DIR` | 关 |
| Offloader debug | `enable_debug_dump` | `OPENJIUWEN_MESSAGE_OFFLOADER_DEBUG_LOG_DIR` | 关 |
| Rule compression dump | `enable_debug_dump` | `OPENJIUWEN_RULE_COMPRESSION_DUMP_DIR` | 关 |
| Recall 内容预算 | - | `OPENJIUWEN_RECALL_MAX_CONTENT_TOKENS` | 8000 |

诊断类目录的解析顺序统一为：显式配置目录 → 环境变量 → workspace 默认目录。

## 压缩上下文的重启恢复

### 核心原理：压缩摘要随消息列表一起持久化

压缩产物（`<memory_block>` 摘要消息）**不是独立存储的**——压缩时 `context.set_messages(new_messages)` 直接替换上下文消息列表，摘要就是其中一条普通消息。因此「重启加载已压缩上下文」等价于「重启恢复 session 的 context state」，无需单独加载压缩产物。

### 持久化与恢复链路

```
【运行时】压缩发生
  context.set_messages(new_messages)     # 消息列表 = prefix + memory_block摘要 + tail
        ↓
【持久化】invoke 结束 / 主动压缩（compress_context）
  context_engine.save_contexts(session) # save_state → {messages, offload_messages, ...}
        ↓  session.update_state({"context": states})
  session.commit() → checkpointer.post_agent_execute(session)
        ↓  AgentStorage.save() → pickle 序列化 → KV store（sqlite / shelve / redis）
═══════════ 服务重启 ═══════════
【恢复】新 invoke，同一 session_id
  session.pre_run() → checkpointer.pre_agent_execute(session)
        ↓  AgentStorage.recover() → 反序列化 → session.state().set_state(state)
  context_engine.create_context(session=session)
        ↓  _load_state_from_session → context.load_state(states)
  message_buffer 重建     # 消息列表含 memory_block 摘要、OFFLOAD / RECALL 标记
        ↓
  下次 get_context_window() 超阈值时，对「摘要 + 新消息」再次压缩
```

关键源码位置：

- `SessionModelContext.save_state / load_state`（`context/context.py`）：导出/恢复 `messages`（压缩后列表）、`offload_messages`（in_memory 卸载缓存）、`last_context_window_access_at`。
- `ContextEngine.save_contexts / create_context`（`context_engine.py`）：经 session state 存取。
- `AgentStorage.save / recover`（`checkpointer/persistence.py`）：整个 session state（含 context 键）pickle 后写入 / 读回 KV store。

### 前提：配置持久化 Checkpointer

**默认 `in_memory`，重启即失忆**。重启恢复必须配置持久化 checkpointer（Runner 初始化时生效）：

```python
from openjiuwen.core.session.checkpointer import CheckpointerConfig
from openjiuwen.core.runner.runner_config import get_runner_config

# sqlite（默认 WAL 模式）
get_runner_config().checkpointer_config = CheckpointerConfig(
    type="persistence",
    conf={"db_type": "sqlite", "db_path": "checkpointer.db"},
)
# 其它后端: {"db_type": "shelve", "db_path": ...}；redis: CheckpointerConfig(type="redis", conf={...})
```

`db_path` 指向重启前已存在的库文件即可恢复历史。

### 各类产物重启后的命运

| 产物 | 持久化位置 | 重启后 | 取回方式 |
|---|---|---|---|
| 压缩摘要（memory block） | session state → checkpointer DB | 随消息列表自动恢复 | 无需操作，已在上下文中 |
| OFFLOAD 占位消息 | session state → checkpointer DB | 自动恢复 | 消息内含 `[[OFFLOAD: ..., path=...]]` 标记 |
| offload 原文 | `{workspace}/context/{session_id}_context/offload/*.json` | 文件天然存活 | 模型按 marker 中的 path 用 `read_file` 读取 |
| recall 归档 | `{workspace}/context/{session}-{hash}_context/compression_recall/` | 文件天然存活 | `[[COMPRESSION_RECALL: id=...]]` 标记 + recall 工具 BM25 检索 |
| compression dump / debug 日志 | workspace 下各目录 | 文件天然存活 | 人工分析，运行时不读 |

三层各自独立存活：**消息列表靠 checkpointer DB，原文与归档靠 workspace 文件**，重启后靠消息内 marker（handle / memory_id / path）与文件重新关联。

### 边界情况

- **workspace 路径稳定性**：offload 文件与 recall 归档均挂在 `workspace_dir` 下。重启后 workspace 路径变化（或重新生成了新目录）时，占位消息仍在（存于 checkpointer DB），但指向的文件找不到——此时模型应按 reload 指引说明无法恢复。使用 core 层 `ContextEngine(config, workspace, sys_operation)` 构造时显式传入稳定 workspace。
- **in_memory offload**：内容存于会话内存缓存 `OffloadMessageBuffer`。`save_state` 会导出该缓存且 `load_state` 重建，因此**配置了持久化 checkpointer 时可随 session state 恢复**；未配置则重启后仅剩占位标记。

## 长会话中途压缩后，最新一轮 cancel / 失败时的新一轮装载

本场景：**同一长会话**中，前几轮已发生过上下文压缩（offload），随后**最新一轮被 cancel 或以异常失败**，紧接着用户开启**新一轮对话**。问题：下一轮模型上下文如何装载？历史压缩数据是否会丢失？

### 关键前提：压缩产物在压缩当时就已持久化，不依赖后续轮是否正常结束

压缩（offload）发生时，原始内容被搬走并被写到**两处**：

1. **原文落盘**：`type=filesystem` 写 `{workspace}/context/{session_id}_context/offload/{processor_type}_{handle}.json`；`type=in_memory` 存进上下文对象的 `OffloadMessageBuffer`。
2. **会话状态（session state）**：主动压缩成功后（`ContextEngine.compress_context`，`context_engine.py:208-213`）紧跟着 `save_contexts(session)` + `session.commit()`。`save_contexts` 把 `context.save_state()` 写入 session 的 `"context"` state，其中**包含压缩后的消息列表（含 `[[OFFLOAD]]` 标记）与 `offload_messages`（in-memory 缓冲映射）**。

因此，只要压缩发生，数据就已经落在了 session state + workspace 文件，**后续那一轮是否正常结束，不影响历史压缩产物的存活**。

### 最新一轮 Cancel 的处理（不破坏历史）

`react_agent.py` 的流式主循环捕获 `asyncio.CancelledError` 后按序执行：

1. `_cleanup_context_on_cancel(session)`：只保留 `with_history=False` 的「当前轮用户提问 + 已完成 tool 对」，丢弃未完成的 tool_call 残留；
2. `_save_contexts_on_cancel(session)`：用 `asyncio.shield(save_contexts(session))` **强制把清理后的上下文保存**，随后才 re-raise。

即：cancel 会刻意"先把本次清理结果落盘"，再让取消向上传播，避免中断时上下文处于未保存状态。

### 最新一轮异常失败的处理

`except Exception` 分支只记录错误并向流写入 error 结果；`finally` 中**仅当 `need_cleanup=True`（本轮新建的 session）才 `save_contexts`**。对**复用中的长会话**（`need_cleanup=False`）失败轮不再额外保存——但这不影响历史压缩，因为前几轮压缩时已 `save_contexts` + `commit` 过，session state 存的是「最后一个成功保存点」，压缩标记与 offload 引用都在。失败轮自身残留的消息可能未落盘，属预期行为（丢的是失败轮残留，不是历史压缩）。

### 新一轮如何装载（同进程连续对话）

新一轮调用 `context_engine.create_context(session=session, history_messages=...)`：

1. `session_id_default_context_id` 仍在 `_context_pool`（未 `clear_context`）→ **复用**原 context 实例，并 `_load_state_from_session(context, session, history_messages)`（`context_engine.py:105`）；
2. `_load_state_from_session` 从 session 的 `"context"` state 读出 `{messages, offload_messages, ...}`，交给 `context.load_state(states)`（`context.py:1072`）：
   - `_message_buffer.rebulid(messages)`：重建消息列表，内容即**上一成功保存点**，含历史压缩后的预览 + `[[OFFLOAD: handle, type, path]]` 标记；
   - 重建 `OffloadMessageBuffer(offload_messages)` 并 `_configure_offload_message_buffer()`绑定 `sys_operation` / workspace / session 信息（供 filesystem 重读）；
   - 若 `history_messages` 非空，用它**覆盖** state 中的消息主体（从长记忆恢复的历史优先）。
3. 后续 `get_context_window()` 物化时，模型窗口中的 `context_messages` 为**压缩后的消息**（每个被 offload 的大消息只是一段头尾预览 + `[[OFFLOAD]]` 标注），**不会自动重新注入原文**；完整内容按需经 `OffloadMessageBuffer.reload(handle, type)` 读取（in_memory 从内存 dict 取；filesystem 按 marker 中的 `path` 用 `fs().read_file()` 读回，见 `message_buffer.py:_reload_from_filesystem`）。

### 风险与注意点

| 情形 | 结果 |
|---|---|
| `type=filesystem` 原文，跨进程/重启 | ✅ 文件在磁盘，天然存活 |
| `type=in_memory` offload，进程未重启 | ✅ 随 session state 的 `offload_messages` 还原 |
| `type=in_memory` offload，进程在保存 state 前被强杀 | ⚠️ reload 返回 `[]`（有 try/except 打 warning，不崩，但原文取不回） |
| filesystem 文件被外部移动/删除 | ⚠️ reload 返回空，不崩，有 warning |
| workspace 路径变化 | ⚠️ 占位消息仍在，但指向的文件找不到，模型按 reload 指引说明无法恢复 |

**结论**：前几轮压缩时数据已随 `save_contexts` + `commit` 落进 session state（含消息的 `[[OFFLOAD]]` 标记与 in-memory offload 映射），最新一轮即使 cancel / 失败也只影响「失败轮自身的残留」，不影响历史压缩；新一轮经 `create_context → load_state` 原样装回上一成功保存点的消息与 offload 缓冲，模型窗口中看到的是带标记的压缩预览，全文按 `handle` / `path` 按需重读。长会话建议使用 `type=filesystem` 并确保 `commit()` 发生，以在 cancel / 失败 / 重启场景下稳定取回原文。

## 小结

- **ContextEngine 是 Agent 层面的成员**，由 Agent 在初始化时创建并持有。
- **上下文处理器**：在消息加入或窗口物化时介入，内置 10 个压缩/卸载处理器，并可通过 `ContextEngine.register_processor` 注册自定义处理器；`processor/forked/` 下另有一组同名重构版（DeepAgent 默认激活），额外提供 compression dump、recall 归档等落盘能力。
- **Agent 使用上下文**：在 `invoke` 中调用 `create_context`、`save_contexts`，委托 Controller 执行。
- **Workflow 使用上下文**：在 Agent 的 invoke 内部，由 Controller 通过 Agent 的 `context_engine.create_context` 创建 context，透传给 `Runner.run_workflow`，Workflow 组件从参数接收 context，**不应自行创建**。
- 通过 `create_context / get_context / save_contexts / clear_context` 完成多会话隔离、多上下文 ID 管理及 Token 级别的窗口控制。
- **压缩落盘**：offload 原文卸载与 recall 归档为功能数据（可回读），compression dump 与各类 debug 日志为诊断数据（opt-in、异常不阻塞主流程）；统一写入 `{workspace_dir}/context/{session_id}_context/` 下。
- **重启恢复**：压缩摘要随消息列表经 session state + 持久化 checkpointer（默认 in_memory，需配置 sqlite / shelve / redis）恢复；offload 原文与 recall 归档为 workspace 普通文件，重启天然存活，靠消息内 marker 与之重新关联。
