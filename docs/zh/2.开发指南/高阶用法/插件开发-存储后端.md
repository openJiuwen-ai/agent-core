# 开发存储后端插件

openJiuwen 的存储层支持通过 Python 标准 entry_points 机制接入第三方 backend，无需修改核心代码。本文说明如何发布一个 vector store 插件，并指出 KV / DB store 的接入方式。

此外，`openjiuwen.extensions.message_queue` 提供了 Pulsar 消息队列适配。它与存储插件的 entry_points 机制无关，本质上是对 Pulsar Python Client 的薄封装；本章末尾单独说明它与后端服务的职责边界。

## 概念

openJiuwen 的存储层分三类：

| 类型 | 抽象类 | 工厂 | 接入方式 |
|------|--------|------|----------|
| Vector | `BaseVectorStore` | `create_vector_store(name, **kwargs)` | entry_points 或显式 `register_vector_store()` |
| KV | `BaseKVStore` | 无 | 用户代码直接 `from X import Y` 实例化 |
| DB | `BaseDbStore` | 无 | 用户代码直接 `from X import Y` 实例化 |

Vector store 之所以有工厂，是因为上层组件（如 KnowledgeRetrieval）需要按名字动态创建。KV / DB 通常是应用代码直接持有的组件，无需名字解析。

## 写一个 vector store 插件

### 1. 继承 BaseVectorStore

```python
# my_package/my_vector_store.py
from openjiuwen.core.foundation.store.base_vector_store import (
    BaseVectorStore, CollectionSchema, VectorSearchResult,
)

class MyVectorStore(BaseVectorStore):
    def __init__(self, connection_uri: str, **kwargs):
        self._uri = connection_uri

    async def create_collection(self, collection_name, schema, **kwargs):
        ...  # 实现所有抽象方法
```

完整接口见 `openjiuwen/core/foundation/store/base_vector_store.py`。插件必须实现所有 `@abstractmethod`。

### 2. 在 pyproject.toml 声明 entry_point

```toml
[project]
name = "my-openjiuwen-vector"
dependencies = ["openjiuwen>=0.1.11,<0.2"]

[project.entry-points."openjiuwen.vector_stores"]
my_backend = "my_package.my_vector_store:MyVectorStore"
```

入口点格式：`name = "module.path:ClassName"`。`name` 是用户在 `create_vector_store(name, ...)` 里传的字符串。

### 3. 发 PyPI

```bash
python -m build
twine upload dist/*
```

### 4. 用户端

```bash
pip install openjiuwen my-openjiuwen-vector
```

```python
from openjiuwen.core.foundation.store import create_vector_store
store = create_vector_store("my_backend", connection_uri="...")
```

## 显式注册（适合私有后端）

如果你的 backend 不准备发到 PyPI，应用启动时手动注册：

```python
from openjiuwen.core.foundation.store import register_vector_store
from my_private_pkg.backend import PrivateBackend

register_vector_store("private", PrivateBackend)
# 之后 create_vector_store("private", ...) 就能用
```

## 名字冲突规则

解析顺序是 **built-in → 显式注册 → entry_points**。built-in 名（`chroma` / `milvus` / `gaussvector`）不可覆盖——插件用这些名字会被忽略。

## 错误处理

- 插件 `load()` 失败：记录 WARNING，`create_vector_store` 返回 `None`，不抛异常
- 插件构造器抛异常：记录 WARNING，返回 `None`
- 所以一个坏插件不会把整个工厂搞崩

## KV / DB 插件

KV / DB 没有工厂。写法：

```python
# my_package/my_kv_store.py
from openjiuwen.core.foundation.store.base_kv_store import BaseKVStore

class MyKVStore(BaseKVStore):
    async def set(self, key, value): ...
    async def get(self, key): ...
    # ... 其他抽象方法
```

用户端直接导入：

```python
from my_package.my_kv_store import MyKVStore
kv = MyKVStore(...)
long_term_memory.register_store(kv_store=kv, ...)
```

## 消息队列后端：Pulsar

`openjiuwen.extensions.message_queue.message_queue_pulsar` 将 SDK 的 `MessageQueueBase` 接口适配到 Apache Pulsar，主要负责：

- 创建和关闭 Pulsar Client、Producer 与 Consumer
- 序列化、发送和接收 `QueueMessage`
- 将异步消息处理函数绑定到订阅，并在处理成功后确认消息
- 复用线程池执行 Pulsar Python Client 的阻塞调用

该模块不是一套独立的消息队列实现，也不在 SDK 进程内保存消息。它依赖一个可访问的 Pulsar 集群；消息发送到 Broker 后，其存储、复制、保留和消费游标均由 Pulsar 后端管理。

### 安装与连接

安装 Pulsar 可选依赖：

```bash
pip install "openjiuwen[pulsar]"
```

创建适配器时只需要提供 Pulsar Broker URL 和执行阻塞客户端调用的线程数：

```python
from openjiuwen.core.runner.runner_config import PulsarConfig
from openjiuwen.extensions.message_queue.message_queue_pulsar import MessageQueuePulsar

mq = MessageQueuePulsar(
    PulsarConfig(
        url="pulsar://localhost:6650",
        max_workers=8,
    )
)
mq.start()
```

应用退出时应调用 `await mq.stop()` 关闭订阅、Producer、Client 和线程池。`stop(drain_timeout=...)` 可以在停止前等待当前消费循环排空，但它不等同于消息重试或死信处理。

### 持久化、重试与死信的职责边界

| 能力 | 负责方 | SDK 适配层的行为 |
|------|--------|------------------|
| 消息持久化、复制与保留 | Pulsar Broker 及其存储后端 | 不落盘，仅调用 Producer 发送消息 |
| 未确认消息的重投 | Pulsar 订阅和 Broker 策略 | 处理成功后调用 `acknowledge`；不实现独立的重试队列或重试调度器 |
| 死信队列（DLQ） | Pulsar Consumer/Namespace 策略 | 不创建死信 Topic，也不配置 `DeadLetterPolicy` |
| SDK 启动失败重试 | `MessageQueuePulsar.start_with_retry()` | 仅重试 Client 初始化；全部失败时可降级到进程内 `FakeMQ` |

因此，业务需要消息投递重试或死信能力时，应在 Pulsar 部署和 Consumer 策略中配置相应机制，并结合消息保留、确认超时、最大重投次数和死信 Topic 做运维监控。`start_with_retry()` 中的 `max_retries` 只表示连接初始化的尝试次数，不能保证某条业务消息被重新投递。

> **注意**：`FakeMQ` 是 Pulsar 不可用时的可选本地降级实现，不具备跨进程共享和 Pulsar 后端提供的持久化、重投、复制或死信保障。生产环境若要求可靠投递，应评估是否允许降级，并根据需求设置 `fallback_to_fake=False`。

## 版本兼容

`Base*Store` ABC 被视为稳定公共 API。破坏性变更至少提前一个小版本宣告。建议插件在 `pyproject.toml` 里对 openjiuwen 小版本加 pin（openjiuwen 目前处于 0.1.x，合入后以实际 release 版本为准）：

```toml
dependencies = ["openjiuwen>=0.1.11,<0.2"]
```
