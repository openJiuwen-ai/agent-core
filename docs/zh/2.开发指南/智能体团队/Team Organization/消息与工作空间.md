# 消息与工作空间

Team Organization 提供两种跨 Team 共享机制：Leader Inbox 传递协商信息，Organization Workspace 保存可交付产物。二者都不能替代 Task Pool 中的正式任务状态。

## Leader Inbox

Leader 消息先写入共享数据库，再发布唤醒事件。事件丢失不会丢失消息；Team 重新绑定时会扫描未确认的 receipt。

| 工具 | 用途 |
|------|------|
| `org_send_leader_message` | 向指定成员 Team 或全体 Leader 发送消息 |
| `org_get_leader_message` | 按 `message_id` 读取消息 |
| `org_list_leader_messages` | 查询当前 Team 的消息和未确认消息 |
| `org_ack_leader_message` | 在处理完成后确认消息 |

广播消息只保存一份正文，但为每个收件 Team 创建独立 receipt。只有 Leader turn 成功处理后才应确认；执行失败或进程中断时不要提前 ack。运行时会按 `message_id` 去重唤醒，但消息处理逻辑仍应具备幂等性。

推荐通过消息传递契约、依赖、风险和阻塞信息。例如：

```text
任务 api-test 依赖接口契约 v3。请在完成 backend-api 后回复产物路径和兼容性说明。
```

不要用消息代替 `org_delegate_task`，否则任务归属、审核和恢复都无法得到一致记录。

## Organization Workspace

`OrganizationWorkspaceManager` 为一个 Organization 和 session 创建共享工作区，并挂载到成员 Team 的工作空间。默认布局表达如下：

```text
organization-workspace/
├── teams/
│   ├── planning-team/
│   └── engineering-team/
└── summary/
```

- 普通 Team 只能写入自己的 `teams/<team_id>/` 目录。
- Summary Team 可读取已绑定的来源产物，并把最终交付写入 `summary/`。
- 成员可以读取协作所需的组织产物，但不应修改其他 Team 的来源文件。
- Workspace Rail 会在工具调用前校验路径，并在适用时记录版本控制提交。

任务的 `output_context` 应保存稳定的产物引用、类型、摘要或哈希，而不是把大段文件内容直接复制进任务记录：

```json
{
  "result_uri": "organization/teams/engineering-team/api-design.md",
  "result_type": "markdown",
  "description": "已评审的 API 设计",
  "result_hash": "sha256:..."
}
```

`organization_id` 会参与工作区路径构造，因此必须通过路径安全校验。跨主机部署时，共享数据库不等于共享文件系统；宿主必须额外提供所有成员可访问的工作空间或产物存储。
