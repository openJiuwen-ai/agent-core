# 组织与任务协作

Organization Task Pool 保存跨 Team 工作的任务树。正式分工必须通过任务完成；Leader 消息只用于协商、依赖和阻塞说明。

## 组织角色

- **Owner Team**：创建 Organization，邀请成员并负责最终解散。
- **Root Leader**：成功认领当前根任务的 Team Leader，负责选择汇总模式和规划子任务。
- **Member Team**：根据能力认领开放任务，或执行委派给本 Team 的任务。
- **父任务创建 Team**：审核其直接子任务，并决定失败后的修复或重新委派。

Owner 与 Root Leader 不一定是同一个 Team。根任务创建者也不一定是 Root Leader。

## 工具一览

Team Organization 共定义 24 个 Leader 工具。文档需要完整列出这些工具，便于开发者理解能力边界和编写 Leader 提示词；但参数字段、返回模型和异常仍应以代码及后续 API reference 为准，开发指南不逐项复制 JSON Schema。

### 组织管理工具

这些工具用于建立协作边界。创建、邀请、激活和解散等管理动作受 Owner 权限约束。

| 工具 | 作用 | 关键约束 |
|------|------|----------|
| `org_create_organization` | 以当前活动 Team 为 Owner 创建 Organization | `organization_id` 必须是安全路径段；一个 Team 不能同时加入两个 Organization |
| `org_invite_team` | 邀请当前 session 中已激活的 Team | 目标必须共享 Owner 的 `TeamDatabase`；当前版本自动接受邀请 |
| `org_dissolve_organization` | 解散组织并清理持久化数据 | 仅 Owner；这是销毁操作，不是完成根任务 |
| `org_list_available_teams` | 列出当前 session 中可邀请的活动 Team | 只发现运行时中已经激活的 Team |
| `org_list_configured_teams` | 列出宿主配置但尚未激活的 Team | 是否可用取决于宿主是否提供 Team activator |
| `org_activate_and_invite_team` | 激活一个已配置 Team 并邀请入组 | 适用于宿主预配置 Team，不用于 AgentGroup 专家模板 |
| `org_list_expert_groups` | 按能力查看宿主发现的 AgentGroup 模板 | 只返回模板信息，不创建 Team |
| `org_create_and_invite_expert_team` | 从 AgentGroup 创建独立专家 Team 并入组 | 仅 Owner；失败时宿主必须回滚临时 Team |
| `org_view_organization` | 查看组织信息及注册的 Team Leader | 调用 Team 必须有权访问目标 Organization |

### 普通成员 Leader 工具

成员 Team 绑定 Organization 后使用以下工具处理任务、审核和消息。

| 工具 | 作用 | 关键约束 |
|------|------|----------|
| `org_view_tasks` | 查看组织任务及与当前 Leader 相关的通知 | 查询不会改变任务或消息状态 |
| `org_create_task` | 创建根任务、子任务、修复任务，或创建时定向委派 | 必须声明非空能力；普通根任务受单活约束 |
| `org_claim_task` | 为当前 Team 认领开放任务 | 仅 `OPEN` 任务；通过原子更新避免重复认领 |
| `org_delegate_task` | 把已分配的非根任务委派给另一成员 Team | 目标是 Organization `team_id`，不能是 teammate 名称 |
| `org_update_task` | 开始、完成、失败、修订任务，或设置根任务汇总模式 | 失败需明确原因；汇总模式只能由 Root Leader 在拆分前设置 |
| `org_view_child_tasks` | 查看父任务的直接子任务和最新审核 | 用于判断父任务完成门禁 |
| `org_view_pending_reviews` | 查看等待当前 Team 审核的已完成子任务 | 只返回当前 Team 有权审核的工作 |
| `org_review_task` | 接受、拒绝或要求修改已完成子任务 | 审核者必须是父任务创建 Team |
| `org_send_leader_message` | 向一个 Team Leader 或全体 Leader 发送可靠消息 | 正式分工仍使用任务；目标是 Team 而非 teammate |
| `org_get_leader_message` | 按 ID 读取一条 Leader 消息 | 读取不会自动确认 |
| `org_list_leader_messages` | 列出当前 Team 的 Leader Inbox | 读取不会自动确认 |
| `org_ack_leader_message` | 在完成消息要求的动作后确认处理 | 应在业务动作成功后调用 |
| `org_create_summary_execution` | 为 `SUMMARY_TEAM` 根任务固定来源并创建一次汇总执行 | 仅 Root Leader；来源必须预先创建且集合不可变 |

### Summary Leader 专用工具

Summary Team 不参与普通任务竞争。它处理汇总任务时只需要以下组织任务工具：

| 工具 | 作用 | 关键约束 |
|------|------|----------|
| `org_summary_get_inputs` | 读取本次 execution 已绑定且验收通过的只读来源快照 | 不能读取未绑定来源或修改来源任务 |
| `org_summary_complete` | 提交最终正文、摘要和可选产物路径，同时完成汇总任务 | 产物路径必须位于 Organization 的 `summary/` 目录 |

## 任务状态

| 状态 | 含义 |
|------|------|
| `OPEN` | 尚未分配，可由能力匹配的成员 Team 认领 |
| `CLAIMED` | 已被 Team 自主认领 |
| `DELEGATED` | 已由上游 Team 定向委派 |
| `IN_PROGRESS` | 执行 Team 已开始工作 |
| `WAITING_SOURCES` | Summary Task 正在等待固定来源就绪 |
| `COMPLETED` | 任务成功完成 |
| `FAILED` | 任务以明确原因终止 |

`CANCELLED` 和 `EXPIRED` 是 `FAILED` 的失败码，而不是独立状态。其他失败码包括 `EXECUTION_FAILED`、`SOURCE_FAILED` 和 `SUMMARY_PROVISION_FAILED`。

典型状态迁移如下：

```text
OPEN -> CLAIMED  -> IN_PROGRESS -> COMPLETED
OPEN -> DELEGATED -> IN_PROGRESS -> COMPLETED
任一活动状态 -> FAILED
```

## 创建、委派和完成

Leader 使用以下工具协作：

| 工具 | 用途 |
|------|------|
| `org_view_tasks` | 查看开放任务、本 Team 任务或组织任务 |
| `org_create_task` | 创建根任务、子任务或修复任务；可以直接委派给成员 Team |
| `org_claim_task` | 为当前 Team 原子认领一个 `OPEN` 任务 |
| `org_delegate_task` | 将已分配的非根任务委派给另一个成员 Team |
| `org_update_task` | 开始、完成、失败任务，设置根任务汇总模式或修订描述 |
| `org_view_child_tasks` | 查看直接子任务及审核状态 |
| `org_view_pending_reviews` | 查看等待本 Team 处理的审核 |
| `org_review_task` | 接受、拒绝或要求修改子任务 |

`required_capabilities` 至少包含一个非空能力标签。运行时会唤醒能力匹配的 Team Leader，但最终是否认领由 Leader 决定。`team_id` 指 Organization 成员 Team，不能传入 Team 内部的 teammate 名称。

## 审核与父任务完成门禁

子任务完成后会生成待处理审核。父任务创建 Team 使用以下结论之一：

- `ACCEPTED`：产物满足要求。
- `REJECTED`：不接受本次产物。
- `NEEDS_REVISION`：需要明确修改。

父任务只有在直接子任务均满足完成门禁时才能完成。若子任务失败或审核未通过，父 Team 应显式创建修复任务，使用 `repairs_task_id` 关联原任务；已验收的修复任务可以替代原失败任务满足门禁。可通过原任务 metadata 中的 `retry_count` 和 `retry_limit` 限制修复预算。

## 未认领任务

Organization 会把未认领策略快照到新任务：

1. `INITIAL_WAIT`：等待能力匹配 Team 认领。
2. `REVISION_PENDING`：超时后通知创建者补充任务描述。
3. `POST_REVISION_WAIT`：描述修订后再次开放认领。
4. `CLOSED`：仍无人认领时，以 `FAILED/EXPIRED` 结束。

创建者收到修订通知后，通过 `org_update_task(action="revise_description")` 提交 `request_id`、当前描述版本和新描述。修订请求与状态转换都是幂等的；不要通过重复创建同名任务绕过流程。
