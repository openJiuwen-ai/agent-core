# 团队验证层（Team Verification Layer）

> **目标：** 在 Leader 汇总结果之前，自动审查团队成员的任务产出质量、正确性和一致性。灵感来源于 Claude Code 的验证子代理。
>
> **适用范围：** 仅 Agent Team 模式（集群模式）。

## 概述

**团队验证层** 是 Agent Team 模式下的一项质量保障机制。当团队成员完成任务时，系统会自动启动独立审查，从六个质量维度评估任务产出，并将结果持久化存储，用于责任追溯和趋势分析。

**为什么重要：**

- **提前发现错误** — 在 Leader 合并可能存在缺陷的产出之前拦截问题
- **保持一致性** — 确保团队成员的工作与团队上下文和需求对齐
- **建立责任机制** — 验证历史记录持久保存在 `TEAM_MEMORY.md` 中
- **驱动数据化改进** — 趋势分析揭示长期薄弱维度

**关键特性：**

| 属性 | 值 |
|------|-----|
| **触发方式** | `TASK_COMPLETED` 事件自动触发 |
| **是否阻塞** | 否 — 异步执行（fire-and-forget） |
| **作用范围** | 按任务、按团队成员 |
| **存储位置** | 团队工作区下的 `TEAM_MEMORY.md` |
| **事件类型** | `team.verification.completed`、`team.verification.error` |

## 工作原理

### 高层流程

```text
用户提出目标 → Leader 组建团队 → 团队成员认领并执行任务
→ 成员标记任务完成 → 验证层触发（异步）
  → VerificationReviewer 评估产出质量
  → 结果存入 TEAM_MEMORY.md
  → 向前端发送事件
→ Leader 汇总结果（验证数据已可用）
```

### 详细步骤

1. **任务完成** — 团队成员完成任务并向 Leader 汇报结果。
2. **验证触发** — `TeamMonitorHandler` 检测到 `TASK_COMPLETED` 事件，通过 `asyncio.create_task()` 异步启动验证。
3. **质量评估** — `VerificationReviewer` 将任务产出发送给配置好的模型，使用结构化提示词评估六个质量维度。
4. **结果存储** — `VerificationMemory` 将结果追加到 `TEAM_MEMORY.md` 的"验证历史"章节。
5. **事件发送** — 发送 `team.verification.completed` 事件，在前端和日志中可见。
6. **Leader 汇总** — Leader 可以在做汇总决策时查询验证趋势。

### 跳过模式

为减少噪音，某些低价值任务会自动跳过验证：

| 模式 | 示例任务 |
|------|---------|
| `heartbeat` | 系统健康检查 |
| `ping` | 连通性探测 |
| `status` | 状态轮询任务 |

可在 `team.verification.skip_patterns` 中配置额外的跳过模式。

## 配置说明

在 `config.yaml` 的 `team` 章节下添加以下配置：

```yaml
team:
  verification:
    enabled: true              # 总开关（默认：true）
    block_on_fail: false       # 验证失败时是否阻塞 Leader 汇总（默认：false）
    auto_rework: false         # 是否自动创建返工任务（默认：false）
    pass_threshold: 70         # PASS 状态的最低分数（默认：70）
    rework_threshold: 40       # 低于此值 = FAIL；介于两者之间 = NEEDS_REWORK（默认：40）
    skip_patterns:             # 跳过的任务标题模式（不区分大小写）
      - "heartbeat"
      - "ping"
      - "status"
```

### 配置参考

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `enabled` | boolean | `true` | 总开关。设为 `false` 时不挂载验证 Rail。 |
| `block_on_fail` | boolean | `false` | 设为 `true` 时，验证返回 FAIL 将阻止 Leader 汇总。 |
| `auto_rework` | boolean | `false` | 设为 `true` 时，NEEDS_REWORK 结果会自动创建返工任务。 |
| `pass_threshold` | integer | `70` | 分数 ≥ 此值 → PASS 状态。 |
| `rework_threshold` | integer | `40` | 分数 < 此值 → FAIL。介于 rework 和 pass 之间 → NEEDS_REWORK。 |
| `skip_patterns` | list[string] | `["heartbeat", "ping"]` | 包含这些子串的任务标题将跳过验证。 |

### 模型客户端

验证层使用团队的默认模型客户端。如果未配置模型客户端，则回退到 **模拟模式** — 返回默认 PASS 结果（分数 75），确保系统开箱即用。

如需使用专用（更便宜/更快）的模型进行验证，可配置模型别名并传递给 `VerificationReviewer`。

## 质量维度

每个任务产出从六个维度进行评估：

| 维度 | 权重 | 检查内容 |
|------|------|---------|
| **正确性（Correctness）** | 25% | 事实准确性、技术有效性、无幻觉 |
| **完整性（Completeness）** | 20% | 需求覆盖度、无遗漏 |
| **一致性（Consistency）** | 20% | 与团队上下文、先前决策和约束的对齐 |
| **清晰度（Clarity）** | 15% | 结构、可读性、逻辑流畅度 |
| **安全性（Security）** | 10% | 风险规避、无不安全模式 |
| **性能（Performance）** | 10% | 效率、无不必要开销 |

### 评分规则

每个维度得分 0–100。总分是加权平均值：

```
overall_score = correctness*0.25 + completeness*0.20 + consistency*0.20
              + clarity*0.15 + security*0.10 + performance*0.10
```

### 状态判定

模型会返回建议状态，但 Rail 会强制执行阈值规则：

| 总分 | 最终状态 | 含义 |
|------|---------|------|
| ≥ 70 | **PASS** | 产出符合质量标准 |
| 40 – 69 | **NEEDS_REWORK** | 产出存在问题；需要修订 |
| < 40 | **FAIL** | 产出不可接受 |

## 验证结果

### 结果结构

```python
class VerificationResult:
    task_id: str           # 唯一任务标识
    task_title: str        # 人类可读的任务名称
    agent_name: str        # 产出该结果的团队成员
    status: str            # PASS | NEEDS_REWORK | FAIL
    overall_score: float   # 0–100 加权平均分
    dimensions: list       # 各维度得分和反馈
    summary: str           # 人类可读的评估摘要
    suggestions: list      # 可操作的改进建议
    timestamp: str         # ISO 8601 时间戳
```

## 记忆与趋势

### 存储位置

验证结果持久化到：

```
team-workspace/TEAM_MEMORY.md
```

在专用的"验证历史"章节下：

```markdown
## 验证历史

### 2026-07-11

#### research_agent — task_001（调研竞争对手定价模型）
- **状态：** PASS
- **分数：** 82/100
- **摘要：** 扎实的研究成果。企业级定价覆盖略有不足。
- **薄弱维度：** completeness (75), performance (70)
- **建议：**
  1. 补充竞争对手 C 的企业级定价。
  2. 将执行摘要压缩为 3 个要点。
```

### 趋势分析

Leader（或任何有权限的 Agent）可以查询质量趋势：

| 指标 | 说明 |
|------|------|
| **通过率（Pass Rate）** | 通过验证的任务百分比 |
| **平均分（Average Score）** | 所有验证的平均总分 |
| **薄弱维度（Weak Dimensions）** | 最频繁低于阈值的维度 |
| **Agent 细分（Agent Breakdown）** | 每个 Agent 的通过率和平均分 |

示例趋势查询结果：

```text
验证趋势（最近 20 个任务）：
- 通过率：75% (15/20)
- 平均分：78.5
- 最常见薄弱维度：completeness
- 通过率最高 Agent：writing_agent (92%)
- 通过率最低 Agent：research_agent (60%)
```

## 事件与前端集成

### 事件类型

| 事件 | 触发时机 | 载荷 |
|------|---------|------|
| `team.verification.completed` | 验证成功完成 | 完整 `VerificationResult` JSON |
| `team.verification.error` | 验证失败（模型错误、解析错误） | 错误信息和任务 ID |

### 前端展示

在 Web UI 中，验证结果展示在：

- **任务详情面板** — 分数徽章和维度细分
- **团队活动流** — 验证事件与任务事件并列显示
- **质量仪表盘**（未来）— 聚合趋势和 Agent 排行榜

### 事件分类

验证事件映射到前端事件展示系统的 `verification` 分类。

## 架构设计

### 组件图

```text
┌─────────────────────────────────────────────────────────────┐
│                    Agent Team 运行时                          │
│                                                              │
│  ┌──────────────┐    ┌──────────────────┐                   │
│  │   团队成员    │───▶│ TeamMonitorHandler │                  │
│  │   完成任务    │    │  (TASK_COMPLETED)  │                  │
│  └──────────────┘    └────────┬───────────┘                  │
│                               │                              │
│                               ▼                              │
│                    ┌─────────────────────┐                   │
│                    │ TeamVerificationRail │                  │
│                    │   (DeepAgentRail)    │                  │
│                    └──────────┬───────────┘                   │
│                               │                              │
│              ┌────────────────┼────────────────┐             │
│              ▼                ▼                ▼             │
│    ┌─────────────────┐ ┌──────────────┐ ┌──────────────┐    │
│    │VerificationReviewer│ │VerificationMemory│ │   事件总线    │    │
│    │  (基于模型的 QA)   │ │ (TEAM_MEMORY.md) │ │ (前端 UI)   │    │
│    └─────────────────┘ └──────────────┘ └──────────────┘    │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 核心组件

| 组件 | 文件 | 职责 |
|------|------|------|
| `TeamVerificationRail` | `rail.py` | 挂载在 Leader 上的 Rail；拦截任务完成事件；触发异步验证 |
| `VerificationReviewer` | `reviewer.py` | 轻量子代理；调用模型并传入结构化提示词；解析 JSON 结果 |
| `VerificationMemory` | `memory.py` | 将结果持久化到 `TEAM_MEMORY.md`；提供趋势查询 |
| `VerificationResult` | `result.py` | 数据模型：结果、状态、维度、分数 |
| `VerificationConfig` | `config.py` | 类型化配置 Schema |

### 集成点

1. **Rail 系统** — `TeamVerificationRail` 继承 `DeepAgentRail`，仅通过 Leader 的 `build_member_rails()` 挂载。
2. **事件系统** — 通过现有的 `TeamMonitorHandler` 事件管道发送 `VERIFICATION_COMPLETED` / `VERIFICATION_ERROR`。
3. **记忆系统** — 使用与其他团队记忆条目相同的格式写入 `TEAM_MEMORY.md`。
4. **配置系统** — 从 `config.yaml` 的 `team.verification.*` 命名空间读取配置。

## 常见问题

**Q：验证会阻塞团队工作流吗？**

A：不会。验证通过 `asyncio.create_task()` 异步执行（fire-and-forget）。Leader 可以在验证仍在运行时汇总结果。未来版本可能支持 `block_on_fail` 以实现更严格的质量门禁。

**Q：如果模型调用失败会怎样？**

A：错误会被优雅捕获，发送 `team.verification.error` 事件，任务正常继续。不会发生阻塞。

**Q：验证可以使用与主 Agent 不同的模型吗？**

A：可以。向 `TeamVerificationRail` 传递专用的 `model_client`。这对于使用更便宜/更快的模型（如 GPT-4o-mini）进行审查非常有用。

**Q：如何禁用特定任务的验证？**

A：在 `config.yaml` 的 `team.verification.skip_patterns` 中添加任务标题模式。默认情况下，匹配 "heartbeat"、"ping" 或 "status" 的任务会被跳过。

**Q：在哪里查看验证历史？**

A：查看 `team-workspace/TEAM_MEMORY.md` 的"验证历史"章节。前端也会在任务详情面板中展示验证事件。

**Q：验证在非团队模式下有效吗？**

A：无效。验证层专为 Agent Team 模式（集群模式）设计。它需要团队事件基础设施和 `TEAM_MEMORY.md`。

**Q：团队成员能看到自己的验证分数吗？**

A：可以 — `TEAM_MEMORY.md` 对所有团队成员只读，因此任何 Agent 都可以查询验证历史和趋势。
